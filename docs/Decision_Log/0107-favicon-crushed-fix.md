# 0107. favicon(タブアイコン)が潰れて見える不具合を、余白付き正方形キャンバスへの修正で解消する

- 日付: 2026-09-10
- 状態: 採用

## Decision

プロジェクトオーナーから、futoing.comのfavicon(ブラウザタブ左のアイコン)
で「ふ、と」のロゴが潰れ、一部が切れて見えるとの報告を受けた。

### 原因調査

`public/images/logo/favicon.svg`(`viewBox="0 0 431 162"`)のpath
バウンディングボックスを計算したところ、`x:[0,430] y:[0,161]`と、
viewBoxのほぼ全域(端から端まで)を占めていることが分かった。つまり
アートワーク自体に余白が一切ない状態だった。

これに加え、ロゴの縦横比が約2.66:1(431:162)と非常に横長であること
が重なり、正方形のfavicon表示枠に収めると:

- 幅を基準に縮小されるため、実際の文字の高さは16pxのアイコンでは
  わずか約6px相当まで潰れる。
- 余白が元から無いため、文字の輪郭がアイコンの端にそのまま接し、
  「切れている」ように見える。

Playwrightで`favicon.svg`をブラウザと同じ`preserveAspectRatio`の
挙動で16/32/48pxに実際にラスタライズして確認したところ、上記の
症状(潰れ+端に接する)を実機相当で再現できた。`favicon.ico`
(6解像度: 16/32/48/64/128/256を内蔵)も同じアートワークから作られて
おり、同様の症状だった。

### 対応

1. **正方形キャンバスへの余白付き配置**: 元のロゴのpath(文字の形
   そのもの)は一切変更せず、`viewBox`を`431×162`から`540×540`の
   正方形に変更し、pathを`translate(54.5 189)`で中央配置した。これに
   より、ロゴの縦横比を保ったまま、キャンバスの短辺・長辺どちらの
   方向にも一定の余白ができる(横方向は約10%、縦方向は横長ロゴの
   性質上さらに広い余白になる)。
2. **favicon.icoの再構成**: 修正後のSVGから16/32/48/64/128/256の
   6解像度をそれぞれ個別にラスタライズし直し、`favicon.ico`を
   再構築した(単純に1枚の画像をリサイズするのではなく、各解像度で
   個別に描画することで、小さいサイズでのアンチエイリアシングの
   質も改善している)。
3. **明暗両背景への対応**: `favicon.svg`に`<style>`で
   `prefers-color-scheme: dark`のメディアクエリを追加し、暗い背景
   (OSダークモード時のタブバー等)では文字色を`#111111`から
   `#f5f5f0`に切り替えるようにした。`favicon.ico`はラスター形式で
   メディアクエリに対応できないため、従来通り`#111111`固定のまま
   (モダンブラウザは`rel="icon" type="image/svg+xml"`のSVG版を優先
   して使うため、実質的な影響は小さい)。
4. **キャッシュ対策**: ファイル名を変更していないため、ブラウザの
   favicon専用キャッシュ(通常のページキャッシュより保持期間が長い)
   が更新後も残る可能性がある。`DefaultLayout.astro`・
   `fieldnote/index.astro`のfavicon参照に`?v=2`というクエリ文字列を
   追加し、URLそのものを変えることで再取得を促すようにした。

### 16pxでの完全な可読性については限界がある

上記の対応により「潰れている・切れている」という不具合(アートワーク
自体が余白ゼロでキャンバス端に接していた問題)は解消したが、16px
という極小サイズでは、ロゴの物理的な縦横比(2.66:1)の制約上、文字の
高さが約5px程度にしかならず、「ふ、と」という文字として読み取れる
状態にはならない(32pxでもまだ厳しく、48px以上で明瞭に読めるように
なる)。これは余白やキャンバスの調整だけでは解決できない、ロゴ自体の
形状に起因する限界であるため、指示に従いロゴのデザイン自体は変更
せず、16px向けの簡略版の案を別途提示するに留めた(下記「他の案」
参照)。

## 採用理由

- 報告された不具合の直接の原因(余白ゼロ+極端な横長比率)を技術的に
  特定できたため、ロゴの意匠(文字の形・線)には一切手を加えず、
  配置(キャンバスと余白)のみを修正する対応で解決できた。
- 16pxでの可読性の限界は、デザインの決定権を持つプロジェクトオーナー
  /ChatGPT(Creative Director)の判断が必要な領域(CLAUDE.mdの役割
  分担)であるため、勝手に簡略化したロゴを実装せず、比較用の案を
  提示するに留めた。

## 他の案

16px専用の簡略版マークとして、以下の2案を検証・提示した(いずれも
既存のpathデータをそのまま再利用しており、新しい線を描き足しては
いない。未実装、承認待ち)。

- **案A: 「ふ」のみ**(ロゴを構成する5つのサブパスのうち、本体+
  左の跳ねストロークの2つを抽出)。曲線が多く、筆致の個性が最も
  強く出る。
- **案B: 「と」のみ**(サブパス1つ、シンプルな単一ストローク)。
  形が単純なため、案Aよりも16pxでの視認性がやや高い。

どちらも32pxで明瞭に判別でき、16pxでも「ふ、と」全体よりはるかに
認識しやすい形として残る。採用する場合、`favicon.ico`は解像度ごとに
異なる画像を埋め込める形式のため、「16px/32pxは簡略マーク、48px以上
はフル『ふ、と』」という解像度別の使い分けも技術的には可能。

## 将来の変更可能性

- 16px向け簡略マークを採用する場合は、`favicon.svg`(メインの参照
  先)をどちらの表示にするか(フルロゴのまま/簡略マークに切替/
  メディアクエリでサイズ別出し分け)を追加で決める必要がある。SVGは
  実装上どのサイズでも同じ内容を表示するため、サイズ別の出し分けは
  `favicon.ico`側でのみ簡単に実現できる。
- 将来ロゴ自体(`logo.svg`)が改訂された場合は、`favicon.svg`の
  pathも合わせて差し替え、同じ余白付き正方形キャンバスの考え方を
  踏襲すること。

## Research Context

小さなタブアイコンであっても、それが「ふ、と」という研究室の入口
であることに変わりはない。壊れた見た目のまま放置せず、まず原因を
技術的に特定し、ロゴの意匠そのものではなく「器(キャンバスと余白)」
側の不備であることを明らかにした上で直せたことは、CLAUDE.mdの
「コンテナとコンテンツを分離する」という設計原則が、ロゴという
一見コンテンツに見える要素にも当てはまる例になっている。
