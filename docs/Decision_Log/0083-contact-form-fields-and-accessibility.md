# 0083. Contactフォームの項目拡充・文言改訂・アクセシビリティ強化

- 日付: 2026-09-04
- 状態: 採用中

## Decision

プロジェクトオーナーから、Contactページについて11項目にわたる詳細な
指示を受けた。大部分はフォームの項目構成・文言・挙動・
アクセシビリティに関する実装指示で、以下のとおり対応した。

### 前提の確認(FormspreeのForm ID)

指示の冒頭で「公開環境のform actionが`YOUR_FORM_ID`のままになって
いる」という前提が示されたが、実際には以下を確認した結果、
`src/config/site.ts`の`formspreeFormId`は既に実際のID(`mvkoqzov`、
PR #39・Decision Log 0076で反映済み)になっており、`YOUR_FORM_ID`と
いう文字列はソースコード上のどこにも残っていない。

- `grep -rn "YOUR_FORM_ID" src/` — 該当なし
- `grep -rn "import.meta.env\|process.env" src/` — 該当なし
  (環境変数は一切使っておらず、Form IDはビルド時に静的HTMLへ直接
  埋め込まれるTypeScript定数のため、Cloudflare Pagesの環境変数設定・
  Preview/Production環境の差・ビルド時の環境変数埋め込みといった
  懸念は、そもそも構造上あてはまらない)
- `npm run build`を実行し、`dist/contact/index.html`を直接確認 →
  `action="https://formspree.io/f/mvkoqzov"`と、正しいIDで出力
  されていることを確認
- 過去のこのセッションでの会話で、プロジェクトオーナー自身が
  実際にフォーム送信を行い、HTTPステータス200・
  `futoing@gmail.com`への着信を確認済み(Decision Log 0076に記録)

以上から、Formspreeの実際のIDは既に正しく反映・動作していると判断
した。新しいフォームの作成や、架空のIDの設定は行っていない。
このセッションのサンドボックス環境からは`formspree.io`・
`futo-site.pages.dev`のどちらへもネットワークポリシーにより接続
できないため、公開URLを直接fetchして確認することはできなかった
(ソースコード・ビルド出力の確認と、過去の実機確認記録から判断)。

### 導入文・注記

- 導入文を「以下のフォームからお気軽にお問い合わせください。」から
  「研究についてのご質問、取材・掲載、協働のご相談などがありましたら、
  こちらからお送りください。」に変更。
- その下に「内容を確認のうえ、通常5日以内にご返信します。」を小さい
  文字(`--fs-sm`)で追加(`.note`)。

### 入力項目

1. お名前(任意) — 既存のまま、ラベルに「任意」バッジを追加
2. ご返信先メールアドレス(必須) — 既存のまま
3. **お問い合わせ種別(任意、新設)** — `<select>`。「選択してください」
   (value=""、誤送信防止のため空文字)/「研究について」/
   「取材・掲載について」/「協働・共同制作について」/
   「イベントについて」/「その他」
4. お問い合わせ内容(必須) — 既存のまま

各項目にplaceholderを追加(お名前「例）山田 花子」、メールアドレス
「例）example@email.com」、お問い合わせ内容「ご相談内容をご記入
ください」)。既存の`<label>`はplaceholderと独立して維持し、
placeholderだけに情報を依存させていない。

「必須」「任意」は共通の`.badge`クラスで同じ見た目に統一。

### プライバシー注記・送信ボタン

送信ボタンの直前に「ご入力いただいた情報は、お問い合わせへの対応にのみ
使用します。」を小さい文字で表示(`.privacyNote`)。同意チェックボックス
は今回の指示どおり実装していない。

送信ボタンは、送信中は`disabled`+ラベルを「送信中…」に切り替える
(`data-submit-label`/`data-pending-label`属性経由)。加えて
`isSubmitting`フラグでの二重送信防止も実装(ボタンのdisabled属性だけに
頼らない多重の防御)。

### 送信結果メッセージ

- 成功: 「お問い合わせを受け付けました。ご連絡ありがとうございます。」
- 失敗: 「送信できませんでした。時間をおいて、もう一度お試しください。」
  (ネットワークエラー・Formspreeからのエラー応答のどちらも同じ文言に
  統一。ユーザーから見て区別する意味が薄いため)

既存の`role="status"`・`aria-live="polite"`をそのまま活用。

### バリデーション

`required`・`type="email"`というブラウザ標準の制約検証をそのまま
利用する方針にした。ブラウザは無効な入力があると`submit`イベント
自体を発火させず、ネイティブのエラー表示(キーボード操作・
スクリーンリーダーの双方に伝わる)を出す。この挙動はJavaScript
無効時にも同じように働く(通常のフォーム送信でも同じ制約検証が
効く)ため、追加の検証ロジックは実装していない。

### Formspree関連

- `_subject`を「ふ、と お問い合わせ」から
  「ふ、と｜ウェブサイトからのお問い合わせ」に変更。
- 「お問い合わせ種別」は`name="category"`を持つ通常のフォーム項目
  のため、Formspreeの通知メールに自動的に含まれる(追加設定不要)。
- 返信先メールアドレスは、既存のとおり`name="email"`の項目を
  Formspreeが自動的にreply-toとして扱う仕組みをそのまま利用。
- `_gotcha`ハニーポットは維持。視覚的には`.honeypot`(clip矩形0)で
  隠し、`tabindex="-1"`でキーボード操作の対象から外し、
  `aria-hidden="true"`でスクリーンリーダーの読み上げ対象からも外して
  いる(実装はDecision Log 0076から変更なし)。
- Formspreeの秘密情報・個人用の認証情報はコードに含まれない
  (Form ID自体は秘密情報ではなく、Formspreeの仕組み上POST先URLとして
  公開されることが前提)。

### デザイン・アクセシビリティ

- `<select>`をinput/textareaと共通の地色・枠線・フォントサイズで
  統一。ブラウザ既定の矢印は`appearance: none`で消し、CSSの
  グラデーションのみで小さな山形を描画(外部アイコン・画像を使わない)。
- input/select/textareaのfont-sizeは`--fs-base`(16px)を維持。
  16px未満だとiOS Safariが入力時に自動でページを拡大してしまうため。
- フォーカス時、既存の枠線色変更(`:focus`)に加えて、キーボード操作時
  のみ`outline`を表示する`:focus-visible`を追加(マウスクリックでは
  出さない)。送信ボタンにも同様の`:focus-visible`を追加。
- 全項目に`<label for>`の関連付けがあることを確認(select含む)。
- 全項目・送信ボタンがTabキーのみで順に操作できることを確認
  (お名前→メールアドレス→お問い合わせ種別→お問い合わせ内容→
  送信ボタン)。

## 採用理由

- ブラウザ標準の制約検証(`required`/`type="email"`)にバリデーションを
  委ねたのは、JS有無に関わらず同じ挙動になり、キーボード・スクリーン
  リーダーの双方に配慮した検証UIを自前で実装する必要がないため。
  CLAUDE.mdの「ライブラリで解決できることに独自実装を持ち込まない」
  方針とも一致する。
- selectの矢印をCSSのみで描いたのは、画像アセットを増やさず、
  「ふ、と」らしい静かな配色(既存の`--color-ink-on-surface`)を
  そのまま流用できるため。
- 成功・失敗メッセージの文言を「時間をおいて、もう一度お試しください」
  に統一したのは、原因(ネットワークかFormspree側か)をユーザーに
  正確に伝える意味が薄く、同じ対処法(時間を置いて再送信)で足りる
  ため。

## 他の案

- 個人情報の取扱いへの同意チェックボックスも検討したが、今回の指示で
  明示的に不要とされたため実装していない。将来的に必要になれば
  `.field`と同じ構造で追加できる。
- エラーメッセージをネットワークエラーとFormspreeエラーで書き分ける
  案もあったが、ユーザーが取るべき行動が同じであるため、シンプルに
  1つの文言に統一した。

## 将来の変更可能性

- お問い合わせ種別の選択肢を増減させたい場合は、`contact.astro`の
  `<option>`を編集するだけで対応できる。
- 個人情報保護方針のページが将来できた場合は、プライバシー注記に
  そのページへのリンクを追加することが考えられる。

## Research Context

フォーム項目を「研究について」「取材・掲載について」など、この研究室
が実際に受け取りうる問い合わせの種類に沿って設計したことは、単なる
入力UIの拡張ではなく、「どんな対話を歓迎しているか」を訪問者に
あらかじめ伝える情報設計でもある。返信までの目安(5日)や、情報の
使用目的を明記したことも、研究室という個人的な営みと、外部との
やり取りという公的な接点との間に、安心して踏み込める余白を作る
試みと言える。
