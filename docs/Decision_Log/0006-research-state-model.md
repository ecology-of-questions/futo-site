# 0006. ResearchStatus を状態遷移込みの Research State Model として設計する

- 日付: 2026-08-04
- 状態: 採用中(0005を拡張)

## Decision

`ResearchStatus`(0005で定義)を単なるUnion型として終わらせず、
どの状態からどの状態へ遷移できるかを `researchStatusTransitions` として
`src/types/research.ts` に併記する。あわせて `canTransitionResearchStatus()`
という遷移可否を判定するユーティリティ関数を用意する。

### State Transition

```
Preparing
    │
    ▼
Reading ─────┐
    │        │
    ▼        │
Writing ─────┘
    │
    ▼
Reviewing
    │
    ▼
Published
    │
    ▼
Archived
```

- 基本の流れ: Preparing → Reading → Writing → Reviewing → Published → Archived
- Writing ⇄ Reading のループを許可(書きながら観察に戻ることがあるため)

## 採用理由

- フィードバックで、状態は単なるラベルの集合ではなく、
  「どこからどこへ動けるか」まで含めて設計してほしいという要望があった。
- 研究のプロセスは一方向の直線ではなく、書きながら読み直す、といった
  行き来があることは、Design Spec 7(Research Attitude)の
  「時の流れに身を任せる」という考え方とも一致する。
- 型(Concept)を先に作り、事例(Data)を後から入れるという考え方が
  「研究でも概念を先に作る」という指摘と重なったため、遷移も
  データが増える前の今のうちに設計しておくことにした。

## 他の案

- **遷移をUIやページ側のロジックとして都度書く案**: 状態遷移の
  ルールが複数箇所に分散し、将来Research Fragment等で同じ状態機械を
  再利用する際に一貫性が崩れるリスクがあるため見送った。
- **ライブラリ(XState等)を使った本格的な状態機械の導入**: 現時点では
  遷移可否を判定できれば十分であり、「不要なライブラリは導入しない」
  方針(キックオフ文書)に反するため、素朴なオブジェクトと関数で実装した。

## 将来の変更可能性(要確認)

- 「レビューでまた文献を読み直す」という話もあったため、
  Reviewing → Reading の遷移が必要になる可能性がある。今回は
  いただいた遷移図(Writing ⇄ Reading のループ)を優先して実装し、
  Reviewing → Reading は含めていない。実際の運用でこの遷移が
  必要そうであれば、この判断を上書きする形で追記する。
- 遷移の判定(`canTransitionResearchStatus`)はまだどこからも
  呼び出していない(実際のステータス変更UIがまだ存在しないため)。
  管理画面やCMS的な仕組みが必要になった時点で利用する想定。

## Research Context

「ふ、と」における研究は、決まった手順を順番にこなす作業ではなく、
書きながら観察に戻る、という往復を含む過程そのものである
(Design Spec 8: 過程こそ主役)。ResearchStatusを単なるラベルの
Union型ではなく、遷移を持つ状態機械として設計したことで、
「研究には後戻りがあってよい」という前提をコードのレベルで
表現できるようになった。これはコンポーネントの見た目ではなく、
データモデルという最も奥まった場所に思想を埋め込む試みである。
