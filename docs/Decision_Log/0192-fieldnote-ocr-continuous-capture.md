# 0192 — Fieldnote OCR: 連続撮影対応・実診断・候補提示への再設計

## Decision

実機(iPhone、Cloudflare Workersプレビュー環境)で「縦書き」選択時にOCRが
「読み取りに失敗しました。お使いのブラウザが対応していない可能性がありま
す。」という一括エラーで失敗する事象が報告された。これを起点に、指示書
「カメラを開いたまま、次々と記録できる」体験改善の要求(6項目)に従い、
OCR機能を以下のように再設計した。

1. **失敗原因を一括表示しない。** `OcrError`に`stage`(`core` /
   `langdata` / `init` / `recognize` / `unknown`)を持たせ、
   tesseract.jsの`logger`が返す`status`文字列を追跡して「どの段階で
   失敗したか」を特定する。UIには常に元の`error.name`/`error.message`
   (300文字まで)をそのまま表示し、要約・一般化しない。
2. **撮影とOCRの待ち時間を分離する。** 撮影(`capturePage()`)は即座に
   `store.addCapture()`で保存し、OCR実行は新設の`OcrQueue`
   (`src/lib/fieldnote/ocrQueue.ts`)にキュー投入するだけで、撮影ボタン
   の再有効化を待たせない。カメラ画面には「保存済み枚数」に加えて、
   控えめな「読み取り待ち」件数を表示する(`#ocr-pending-count`)。
3. **OCRの同時実行を防ぎ、状態を永続化して安全に再開する。**
   `OcrQueue`は単一実行(1件ずつ順番に処理)。各撮影の`ocrStatus`
   (`pending` / `processing` / `done` / `failed`)をIndexedDBに保存し、
   アプリ起動時に`listUnfinishedOcrCaptures()`で未完了分(`pending`/
   `processing`双方。画面を閉じた後も処理が続いているとは仮定せず、
   `processing`のまま残っている記録は「中断された」ものとして再度
   キューに積み直す)を再投入する。二重投入は`OcrQueue`内の
   `Set`によるID重複排除で防ぐ。
4. **読み取り結果を「候補」として扱う。** 新設の`ocrCandidateText`/
   `ocrCandidatePage`フィールド(`FieldnoteCapture`)にのみ結果を書き
   込み、既存の`excerptText`/`pageLabel`は自動上書きしない。UIの
   「この内容を抜粋に使う」/「ページ欄に使う」ボタンを押した場合のみ、
   既存のblur保存ハンドラと同じ`persistExcerpt`/`persistPage`関数を
   呼び出して反映する(書き込み経路を一本化)。マーカー範囲の自動抽出は
   指示書の通り今回は実装しない。
5. **画面を簡潔にする。** 技術的な説明・詳細エラーは`<details>`
   (「詳細」)に格納し、既定では折りたたむ。「保存しました」表示は
   実際に`persistExcerpt`/`persistPage`の`await`が解決した後にのみ
   出す。OCR失敗時も撮影した写真自体は残し、再試行ボタン
   (`data-ocr-run`)と手入力(既存の抜粋欄)への導線を維持する。
6. **実機非対応の疑いへの対策。** `wasm-feature-detect`の`simd()`で
   WebAssembly SIMD対応を実測し、非対応環境では非SIMD版コア
   (`tesseract-core-lstm.wasm.js`、新規に自己ホスト追加)を使う。
   判定自体が失敗した場合はSIMD版を既定にする(安全側)。

## 検証・未検証事項

**検証済み(このセッション内、Chromiumの自動テストによる):**
- 3枚連続撮影がOCR完了を待たずに完了すること(撮影ブロッキングなし)。
- 撮影後にキューが順番に処理され、完了後は「読み取り待ち」表示が消える
  こと。
- 撮影セッション終了後、各カードのOCR状態が最終状態(完了/失敗)に
  収束すること。
- アプリを閉じた状態を模した「`pending`のままIndexedDBに残った撮影」
  を、再読み込み後に`resumeUnfinished()`が検出し、自動的に処理を再開
  すること(実際に文字認識が最後まで走り、`ocrCandidateText`が保存
  されることを確認)。
- 実際の日本語手書き風テキスト画像に対して、OCR候補が表示され、
  かつ**自動では**既存の抜粋欄(空)を書き換えないこと。
- 「この内容を抜粋に使う」を押した後にのみ抜粋欄が更新され、保存が
  実際に完了した後にのみ「保存しました」が表示されること。
- 上記の状態が、履歴画面経由での再読み込み後も保持されること(永続化)。
- 既存のFieldnote機能(抜粋・コメント・関連リンク・コレクション・
  エクスポート/インポート等、23項目)に回帰がないこと。
- サイト全体のレスポンシブ・エラー無し確認(320/390/1440px、全15
  ページ相当)に回帰がないこと。
- `npx astro check` / `npx tsc --noEmit` / `npm run build`が
  エラー・警告(既存の1件を除く)なく通ること。

**未検証(このセッションでは確認できない):**
- 実際に報告のあった実機(iPhone、Cloudflare Workersプレビュー環境)
  上で、今回の変更後にOCRが実際に失敗しなくなったかどうか。今回の
  対応は「原因を推測して一つに決め打ちで直した」のではなく、
  (a) 実機で失敗しても具体的な原因(段階+元のエラー文言)が見える
  ようにする、(b) WebAssembly SIMD非対応という、実機での既知の
  失敗要因になりうる条件を実測・回避できるようにする、という診断性・
  堅牢性の底上げである。**合成画像でのテスト成功だけをもって「実機
  修正済み」とは判断しない**(指示書の明示的な要求どおり)。次に
  同じ実機で3ページ連続撮影を試し、(直った場合は完了、直らない場合は)
  「詳細」に表示される段階名・エラー文言を確認してもらう必要がある。
- 縦書きOCRの認識精度自体は本対応の対象外(Decision Log 0188で
  既知の課題として記録済み)。今回の変更は「失敗時に何が起きたか
  分かるようにする」ことが目的であり、認識精度そのものの改善では
  ない。

## 採用理由 (Rationale)

- 「ブラウザ非対応」への一括集約は、実際に何が起きているかを利用者
  からもプロジェクトオーナーからも見えなくしてしまい、次に同じ問題が
  起きた時にまた一から調査し直すことになる。段階+元のエラー文言を
  そのまま出すことで、次回以降は「詳細」を見るだけで切り分けができる
  ようにした。
- 撮影とOCRを同期的に結合したままだと、「次々と記録できる」体験は
  原理的に実現できない(1枚ごとに数秒〜十数秒のOCR待ちが発生する、
  Decision Log 0187の実測を参照)。キューによる分離は、この制約下で
  体験を成立させる直接的な解決策である。
- 「候補」パターン(自動反映しない)は、この機能全体の設計思想
  (OCRは下書きの提案に過ぎない、Decision Log 0188)と一貫しており、
  かつ「既存の抜粋や自分のコメントを自動で上書きしない」という
  指示書の明示的な要求そのものでもある。

## 他の案 (Alternatives)

- 常時動画OCR(フレームを継続的に処理し続ける方式)も検討したが、
  指示書で明示的に「常時動画OCRではなく、撮影した静止画を順番に
  読み取る方式」と指定されているため採用しなかった。静止画方式は
  処理量・電力消費の面でも1枚ずつのほうが実機での安定性を見積もり
  やすい。
- OCRキューを撮影ごとに複数同時実行(並列化)する案も検討したが、
  「処理は順番に、安全に再開する」という指示書の要求と、実機
  (特にモバイル)でのWebAssembly処理の並列実行はメモリ・CPU負荷の
  面で不安定になりやすいという判断から、単一実行のキューとした。

## 将来の変更可能性 (Future changes)

- マーカー範囲の自動抽出(指示書4項目目で「基本動作が安定するまでは
  必須にしない」とされたもの)は、今回の基本フロー(撮影→キュー→
  候補→採用)が実機で安定したことを確認した後に、別のDecision Logで
  検討する。
- 実機での再検証の結果、SIMD/非SIMD切り替え以外の要因(例:
  ネットワーク環境、Safari固有のWeb Worker制約等)が判明した場合は、
  この0192に追記するのではなく、新しいDecision Logエントリを起票し、
  本エントリはそのまま維持する(過去のエントリを書き換えない原則)。

## Research Context

このスタジオは「完成させること」ではなく「育て続けること」を目的と
している。今回の対応も、実機での失敗を一度で「直しきった」と主張する
のではなく、失敗したときに何が起きているかが見える状態を作り、次の
実機検証でその情報をもとに次の一手を判断できるようにした、という
意味で、継続的な研究・改善のプロセスそのものである。
