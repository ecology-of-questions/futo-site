# 0018. Heroのビジュアルを画像の縦横比に合わせ、見出しの改行を固定する

- 日付: 2026-08-08
- 状態: 採用中

## Decision

`npm run dev` での実機確認を受け、Hero周りで見つかった3つの表示上の
問題を修正した。

1. **見出しの改行**: `headingLines` の2行目「そこに問いがある。」
   (9文字)が、デスクトップ幅では左カラムの横幅ぎりぎりで、ブラウザの
   自動折り返しが意図しない文字位置(「あ」の直後)で発生していた。
   `headingLines` を3行(`["気づいたら、", "そこに", "問いがある。"]`)
   に分割し、どの行も自動折り返しが起きない長さにした。あわせて
   `.heading` に `word-break: keep-all` を設定し、`<br>` 以外の位置で
   CJKテキストが折り返されないようにした。
2. **VisualFragmentのobject-fit**: `03_top_page_artwork.png`
   (1536×1024、透過範囲あり)を、正方形に近いHeroのビジュアル枠に
   `object-fit: cover` で収めていたため、枠のアスペクト比に合わせて
   画像の左右がトリミングされ、イラスト本体(キャンバス中央〜やや
   右寄りに集中)の右端が不透明な領域の途中で切れて見えていた。
   `object-fit: contain` に変更し、画像全体をトリミングせずに表示する
   ようにした。
3. **Heroビジュアル枠のアスペクト比とカラム比率**: 2の`contain`化だけ
   では、正方形に近い枠に横長画像を収めると上下に大きな余白ができて
   しまう(画像自体は縮小されるだけで、枠が画像を包む形にならない)。
   `.visual`(デスクトップ)に `aspect-ratio: 3 / 2` を設定して画像と
   同じ比率の枠にし、`contain`が実質的に隙間なく画像を敷き詰める形に
   した。ただし、コピー列の幅を `42%` のまま固定していると、
   ビジュアル列の絶対幅が変わらないぶん3:2の枠は以前より縦に短く
   なるだけで、コピー列の高さ(見出し3行+本文+リンク+Scroll)との
   差分がそのまま余白として残ってしまう。これを緩和するため、
   `grid-template-columns` を `42% 1fr` から `minmax(280px, 22rem)
   1fr` に変更し、コピー列は「読みやすさを保てる範囲」に固定して、
   残りの幅をできるだけビジュアルへ渡すようにした。

## 採用理由

- 見出しの改行位置は、Hero.astroのpropsコメントに「改行位置はコピーの
  意図そのものなので変更しない」と明記されている。裏を返せば、
  ブラウザが意図せず追加の改行を挿入することは、その方針に反する
  バグだと判断した。改行位置を`headingLines`側で確実に制御し、CSS
  (`word-break: keep-all`)で二重に保証する形にした。
- VisualFragmentは「画像形式を問わない差し替え可能なスロット」
  (Design Spec 11)として汎用設計されている。`object-fit`の選択
  (cover/contain)は画像そのものをどう見せるかという実装判断であり、
  「画像を切らずに全体を見せる」というcontainの挙動は、透過範囲が
  広く繊細なイラストと相性が良いと判断した。
- アスペクト比・カラム比率の調整はHero.module.css側(Hero固有の
  レイアウト判断)に閉じ、VisualFragment自体は変更していない。将来
  別の画像(異なる比率)に差し替わった場合も、VisualFragmentは
  そのまま再利用でき、Hero側の`aspect-ratio`だけを見直せばよい。
- コピー列を`%`から`minmax(280px, 22rem)`という絶対値ベースの範囲に
  変えたのは、モックアップ由来の「42%」という数値そのものより、
  「本文が折り返さずに読める幅を確保する」という意図の方が本質だと
  判断したため。既存の本文コピーの最長行(19文字程度)が折り返さない
  下限を確認した上で、280px(下限)〜22rem=352px(上限)という範囲に
  収めた。

## 他の案

- **枠をコピー列の高さ(587px前後)に完全に合わせる案**: 3:2の比率で
  587px の高さを得るには幅880px前後が必要になり、1120px幅のHero内では
  コピー列が200px程度まで潰れてしまい、本文が読めなくなる。今回は
  見送り、コピー列の可読性を優先した(余白が残ることは許容した)。
- **ビジュアルをHero全体の右端(ビューポート端)までフルブリードさせる
  案**: 3:2の枠をコピー列の高さに近づける上ではより効果的だが、
  「中央寄せ・max-width固定」というHero全体のレイアウトパターンを
  崩す大きな変更になる。Design Spec・モックアップに明記のない
  視覚的な方向転換であり、実装判断の範囲を超えると判断し、今回は
  見送った。将来的に検討する場合はChatGPT側のレビューを挟みたい。
- **`.visual`の高さをJavaScriptでコピー列の実測高さに合わせる案**:
  達成度は高いが、レイアウトのためだけにJSを導入することになり、
  「アニメーションライブラリ不使用・素朴な実装を優先する」という
  Architecture方針に反するため見送った。

## 将来の変更可能性

- ビジュアル画像を差し替える際、縦横比が3:2から変わる場合は
  `.visual`の`aspect-ratio`の値も合わせて見直す必要がある。
- コピー列とビジュアル列の高さの差(余白)を完全になくしたい場合は、
  フルブリードレイアウトへの変更をDesign Spec側で検討することになる
  (Parking Lot相当ではないが、視覚的な方向性の変更としてChatGPT側の
  判断を仰ぐのが妥当)。

## Research Context

「静かな雑誌」(Design Spec 9)という方向性は、余白を単なる隙間では
なく思考時間として扱うことを前提にしている(tokens.css)。今回、
ビジュアル下に残った余白を完全にゼロにする道(フルブリード化)を
選ばず、コピー列の可読性を守った上で「無理のない範囲で大きく」に
留めたのは、その思想と一致する判断だと考えている。
