# 0197 — OCR比較ツールの認証方式をAPIキーからADCへ変更

## Decision

Decision Log 0196で用意したOCR比較ツール(`scripts/ocr-compare/`)の
Google Cloud Vision認証方式を、APIキーから**Application Default
Credentials(ADC)**へ変更した。プロジェクトオーナーから「比較段階では
APIキーを発行する方式ではなく、自分のPC上でGoogleにログインして実行する
認証方式にしてほしい」という明示的な要望を受けたもの。

**Decision Log 0196の該当箇所(APIキー方式の設定手順の記載)は、この
変更により実質的にsupersededとなる。** Decision Log 0196自体は削除・
書き換えず、そのまま残す(このリポジトリのDecision Logルールに従い、
過去のエントリは編集しない)。

## 変更内容

`scripts/ocr-compare/engines/google-vision-engine.mjs`:
- `GOOGLE_VISION_API_KEY`環境変数を読む方式を廃止。
- 代わりに、本人が自分のPC上で`gcloud auth application-default
  login`を実行して発行するADCを使う。スクリプトは
  `gcloud auth application-default print-access-token`を子プロセスで
  呼んでその場限りのアクセストークンを取得するだけで、トークン自体は
  保存・ログ出力しない。
- ユーザー認証情報(サービスアカウントではない)でVision APIを呼ぶ
  場合に必要な、課金対象プロジェクトの指定(`X-Goog-User-Project`
  ヘッダー)にも対応した。プロジェクトIDは`GOOGLE_CLOUD_PROJECT`
  環境変数、無ければ`gcloud config get-value project`から取得する。
- `gcloud`未インストール・未ログインの場合は、送信を試みずスキップを
  報告する(挙動はAPIキー方式のときと同じ、変わらない)。

**このツールはこの性質上、本人のPC(このリポジトリをcloneした端末)上で
実行する必要がある。** クラウド上の実行環境(このセッションを含む)には
本人のGoogleアカウントでログインする手段が無いため。

## 現在の比較対象・進捗

- **対象は、プロジェクトオーナーから提供された実写真1枚
  (ページ137、実際にiPhone実機でOCRが失敗した写真)。**
- 切り抜き範囲(ページ部分のみ、背景・手を除外)を提示し、確認を得た。
- 正解文の下書き(連続する3列、右→左)を提示済みだが、**本人による
  確認・修正がまだ済んでおらず、正解文としては未確定。**
- Tesseract側は、この切り抜き画像で実測済み(ローカル実行、約2.9秒)。
  実際の出力はチャットでのみ共有し、コミット・Decision Logには含めて
  いない。
- Google Vision側は、ADC認証が(このセッションには)無いため未実施。
  本人のPC上での実行を待っている。

**Fieldnote本体(`src/lib/fieldnote/*`)のOCR実装は、この比較結果を
確認するまで変更しない。**

## 採用理由 (Rationale)

- 認証情報の発行・保管をAPIキー(コピー&ペーストで扱う値)ではなく、
  本人のPC上の`gcloud` CLIに一本化することで、認証情報がこのやり取り
  (チャット・コミット・共有される可能性のある環境変数)を経由する
  機会自体を無くせる。指示書の「APIキー等はコード・リポジトリに
  含めない」という要求を、より確実に満たす設計だと判断した。
- 比較スクリプトを本人のPC上で実行する前提に変えたことで、
  「本人のGoogleアカウントでの認証」という行為自体も、クラウド上の
  実行環境を経由せず、本人が完全に把握できる環境で完結する。

## 他の案 (Alternatives)

- サービスアカウントキー(JSONファイル)を使う方式も検討したが、
  ファイルとして保存・受け渡しする必要があり、APIキーと同種の
  「値を扱う」リスクがあるため、本人の要望(ログインベースの認証)
  により合致するADCを選んだ。

## 将来の変更可能性 (Future changes)

- 実際にGoogle Vision側の比較が実施でき次第、結果を新しい
  Decision Logエントリで報告する。
- 比較結果次第でFieldnote本体への統合を検討する場合、その時点で
  改めて認証方式(本番でどう認証情報を管理するか)を設計する
  (指示書の「PreviewとProductionの認証・課金設定は分ける」という
  要求に基づき、この比較ツールのADC方式とは別に検討する)。

## Research Context

認証方式そのものを、本人の要望に応じてこの段階で作り直したことは、
「誰が何を管理するか」を曖昧にしないという、このプロジェクト全体の
一貫した姿勢(Decision Log 0141・0143等の本番/Worker認証の扱いにも
通じる)を、比較実験という小さな範囲でも徹底したものである。
