# 0196 — OCRエンジン比較の準備(現状確認・読み順の切り分け・比較ツール)

## Decision

Fieldnoteの縦書きOCRが実用に達していない問題について、Tesseract.jsの
周辺実装を際限なく調整し続けるのではなく、既存の他のOCRエンジン
(第一候補: Google Cloud Vision DOCUMENT_TEXT_DETECTION)と実写真で
比較し、修正の手間が少ない方式を選ぶ、という指示書に基づき、比較の
準備を行った。**この時点では、本番の既定エンジンは変更していない。**

## 1. 現状確認(過去の報告を鵜呑みにしない)

- **PR #114〜#119は、GitHub上で全件`open`(未マージ)であることを
  実際に確認した。** #114(base: main)→#115→#116→#117→#118→
  #119(現在のHEAD、base: `claude/bookshelf-cover-policy-v3`)という
  スタック構造も維持されている。過去の会話内の報告ではなく、この
  確認時点でのGitHub上の実際の状態として記録する。
- **現行のTesseractモデル・設定**(`src/lib/fieldnote/ocr.ts`):
  - モデル: `jpn`(横書き)/ `jpn_vert`(縦書き)、いずれも量子化版
    (`best_int`)。Decision Log 0193で確認済みのとおり、両者の
    展開後サイズはほぼ同一(差700バイト程度)で、縦書き専用に
    再学習された別の認識ネットワークではなく、横書きとほぼ同じ
    LSTM認識ネットワークに向き別の設定が乗っているだけと考えられる。
  - PSM(Page Segmentation Mode): 横書き6(均一な1ブロックの
    テキスト)/ 縦書き5(均一な1ブロックの縦書きテキスト、
    Tesseract公式が縦書きCJK向けに推奨する値)。
  - 画像の回転・切り抜き: Decision Log 0195で追加した固定ガイド枠+
    任意の手動回転(±30度、平面内回転のみ)。自動のページ境界検出・
    台形補正は無い。
  - 出力の整形処理: `data.text.trim()`のみ。それ以外の後処理(並べ替え・
    フィルタリング等)は一切行っていない。

## 2. 「縦列の先頭を横に拾ったように見える」症状の切り分け

指示書の要求どおり、スクリーンショットだけで原因を断定せず、
Tesseract.jsの生の構造化出力(`data.lines`、各行のバウンディング
ボックス)を直接調べた(既存の実写真1枚、ページ範囲に切り抜き済みの
ものを使用。Node.js上で本番と同じ自己ホスト済みアセット・同じPSM設定
で実行)。

**結果: 読み順(列の順序)そのものは正しかった。**
- 検出された15本の「行」(縦書きでは1本の縦列が1行として扱われる)の
  中心x座標は、右→左へ単調に減少しており(619→17、許容誤差15px以内で
  逆行0件/14区間)、Tesseractの構造化データの時点で正しい列順になって
  いることを確認した。
- `data.text`(実際にFieldnoteへ表示される文字列)も、この15行構造を
  そのまま改行区切りで結合したものと完全に一致していた(行数15・
  文字数503字とも一致)。**Fieldnote側のコード(`data.text.trim()`の
  みで、他の後処理は無い)が読み順を壊している、という可能性は
  この検証で否定された。**
- 一方で、`data.text`の中には(列と列の間の改行とは別に)半角スペース
  文字が36箇所見つかった。これは縦書きの1列の**内部**に、Tesseractの
  単語分割処理が挿入した区切りである可能性が高い(縦書き日本語には
  本来、単語間の空白という概念が無いため)。見た目上「文字が飛び飛びに
  ばらけている」ような印象を与える一因と考えられる。

**結論: 「読み順の崩れ」ではなく、(a)列内部の文字認識誤り(実際、
複数の列でTesseract自己申告のconfidenceが低い・0%のものがあった)と
(b)列内部への不要な空白挿入、の2点が主な症状の実体だと判断した。**
これは推測ではなく、上記の構造化データの実測に基づく。

この調査の範囲では、明確な「設定バグ」(直せば即改善するような
コードの誤り)は見つからなかった。空白挿入は、Tesseract自体の
単語分割ロジックに起因するもので、Fieldnote側の設定ミスではない。
指示書の「長期のTesseract調整作業へ広げない」という方針に従い、
この時点ではコードの修正は行わず、比較の基準・記録としてのみ残す。

## 3. 比較ツールの準備

`scripts/ocr-compare/`(公開サイトのビルドに含まれない、
`src/`の外に置いたローカル専用ツール)を新設した。

- `engines/tesseract-engine.mjs`: 現行のFieldnote実装と同じ自己ホスト
  済みアセット・同じPSM設定で、Node.js上でTesseract.jsを実行する
  (完全にローカル、外部送信なし)。
- `engines/google-vision-engine.mjs`: Google Cloud Vision
  DOCUMENT_TEXT_DETECTIONをREST API(APIキー認証)で呼び出す。
  `GOOGLE_VISION_API_KEY`環境変数が無い場合は、**送信を試みずに
  その旨を報告するだけ**にしてある(認証情報が無いことをごまかして
  「測定できた」ことにしない、という指示書の要求どおり)。
- `cer.mjs`: 文字誤り率(編集距離÷正解文字数)の計算。
- `compare.mjs`: 実行スクリプト。`--with-google`を明示的に指定しない
  限りGoogle Cloud Visionは呼ばない(誤操作での送信を防ぐための
  二重の歯止め: フラグ+環境変数の両方が必要)。認識結果の全文は
  既定では表示せず、集計値(所要時間・文字誤り率)のみを出力する。

**動作確認**: Tesseract側は実際に動作させ、既存の実写真1枚
(ページ範囲に切り抜き済み、縦書き)で以下を実測した(**正解文が
まだ無いため、文字誤り率は未測定**。写真本文・認識結果は記録しない)。

| 画像ID | 方式 | 処理時間 | 文字誤り率 |
|---|---|---|---|
| photo-01(切り抜き済み) | Tesseract | 約3.5秒 | 未測定(正解文が無い) |
| photo-01(切り抜き済み) | Google Vision | 未実施(認証情報が無い) | 未測定 |

Google Vision側は、認証情報が無いため送信を試みていないことを、
実際に`GOOGLE_VISION_API_KEY`を未設定のまま実行し、スクリプトが
安全にスキップすることを確認した(下記「未実施・ブロッカー」参照)。

## 4. Google Cloud Vision料金(公式ページに基づく試算)

`https://cloud.google.com/vision/pricing`(2026年9月時点、WebSearchで
複数の情報源と突き合わせて確認)より、DOCUMENT_TEXT_DETECTIONの料金:

| 月間ユニット数 | 単価 |
|---|---|
| 1〜1,000ユニット/月 | 無料(毎月リセット) |
| 1,001〜5,000,000ユニット/月 | $1.50 / 1,000ユニット |
| 5,000,001ユニット以上/月 | $0.60 / 1,000ユニット |

1ユニット=1枚の画像に対する1回の認識(再試行も1ユニットとして
カウントされる)。この無料枠はVision APIの機能全体で共有される
(プロジェクト単位)。

**試算(Fieldnoteの想定利用規模、本人利用のみを前提):**

| 月間撮影枚数 | 月額費用試算 |
|---|---|
| 100枚 | $0(無料枠内) |
| 500枚 | $0(無料枠内) |
| 1,000枚 | $0(無料枠ちょうど) |
| 1,200枚(再試行200回を含む想定) | 約$0.30(200ユニット×$1.50/1000) |

**本人限定の個人利用という前提であれば、通常の使い方では無料枠に
収まる可能性が高い**、というのが試算からの結論。ただし、これは
比較実験の試行回数や、将来の利用頻度の変化を含んでいない。予算
アラートの設定はGoogle Cloud Console側で別途可能だが、これ自体は
支出の上限ではなく通知であることに注意する必要がある(指示書の
指摘どおり)。

## 未実施・ブロッカー(次にお願いしたいこと)

指示書の要求どおり、**推測で進めず、必要なものを具体的に依頼する。**

1. **実写真の追加提供。** 現在手元にあるのは、以前いただいた1枚
   (縦書き、背景に他の書類・物が写り込んだもの)のみ。指示書が
   求める比較(普通の縦書き・マーカーあり・見開きや湾曲を含む条件、
   計3〜5枚)には不足している。追加の実写真をお願いしたい。
2. **正解文の準備。** 比較対象範囲について、実際に本を見て確認した
   正解文が必要(このツール自身やAIによる文字起こしを、未確認のまま
   正解文として使うことはしない、という指示書の要求どおり)。写真を
   追加でいただく際、該当範囲の正解文(短い抜粋で構いません)も
   合わせてご用意いただけると、比較が進められる。
3. **Google Cloud Vision APIの認証情報・課金設定。** 現時点で
   `GOOGLE_VISION_API_KEY`は未設定(このサンドボックスにも、当方にも
   Google Cloudの認証情報は無い)。上記「Google Cloud Visionの設定」
   (`scripts/ocr-compare/README.md`)の手順でAPIキーを発行し、
   **このチャットには貼らず**、実際に比較を実行する端末の環境変数と
   して設定していただく必要がある。
4. **既にいただいた1枚の写真を、Google Cloud Visionへ送信してよいか
   の確認。** 上記の料金試算(1回の送信は無料枠内)を踏まえたうえで、
   「この写真の、ガイド枠相当に切り出した範囲」をGoogle Cloud Vision
   へ送信することについて、明示的な同意をいただきたい。チャットに
   写真を貼っていただいたこと自体は、Googleへの転送への同意とは
   みなしていない(指示書の要求どおり)。

上記が揃い次第、比較表(画像ID・方式・切り抜き条件・処理時間・
文字誤り率・列順の誤り・抜け重複・ページ番号・修正の手間)を実測値で

## 採用理由 (Rationale)

- 「読み順の崩れ」という当初の仮説を、生の構造化データで検証した
  ところ否定されたことは、指示書の「スクリーンショットだけで原因を
  断定しない」という要求が実際に効果を発揮した例である。仮に検証
  せずGoogle Vision導入を急いでいたら、実際には解決しない問題
  (列内部の認識誤り・空白挿入)を「エンジンを変えれば直る」と誤って
  期待していた可能性がある。
- 比較ツールを、認証情報・同意が無い状態でも安全に(誤送信せずに)
  動作するよう設計したのは、指示書の「無断で外部送信しない」という
  一貫した方針(Decision Log 0187から続く)を、比較実験という新しい
  文脈でも維持するため。
