# 0193 — 実機での縦書きOCR精度不足の調査(速度は良好、精度が課題)

## Decision

PR #119(Decision Log 0192)を実機(iPhone)で確認したところ、連続撮影の
操作感・処理速度は十分だが、**縦書きの認識精度が不十分**という報告を
受けた。指示書の5項目に沿って調査した結果を以下に記録する。

## 調査結果

### 1. 連続撮影・再訪後も「縦書き」指定は正しく引き継がれているか

**問題なし(コード確認済み)。** 向きは撮影の瞬間に`capturePage()`
(`src/lib/fieldnote/app.ts`)が`sessionOcrOrientation`から
`capture.ocrOrientation`へ書き込み、以後は常にIndexedDBに保存された
その値を読む一本の経路になっている。

- 通常のキュー処理(`OcrQueue.processOne()`)も、再訪時の再開
  (`resumeUnfinished()` → 同じ`processOne()`)も、同じ
  `capture.ocrOrientation`フィールドを参照する。
- 手動再試行ボタン(`buildOrientationSelect`)も、押した時点で選択
  されている値を`runOcr()`経由で同じフィールドに書き戻してから実行
  する。
- Playwrightで、縦書きを選んで撮影→履歴から再度開く→再試行ボタンの
  向き選択が「縦書き」のまま保持されていることを確認した。

**向きが失われて横書き扱いになっている、という筋ではないと判断した。**

### 2. 縦書き用モデル・PSMが実際に使われているか

**実際に使われていることをネットワークログで確認した。** 縦書きで
OCRを実行した際、`lang-data/jpn_vert.traineddata.gz`への実際のリクエスト
(200)が発生し、`jpn.traineddata.gz`は要求されないことを確認した
(`src/lib/fieldnote/ocr.ts`の`langForOrientation()`が向きに応じて
別の言語コードを渡している、その通りの動作)。PSM(Page Segmentation
Mode)も縦書き時は`"5"`(単一の縦書きブロック)を設定しており、
Tesseract公式ドキュメントが縦書きCJK向けに推奨する値と一致している。

**ただし重要な事実として記録する:** `jpn.traineddata`(横書き)と
`jpn_vert.traineddata`(縦書き)は、展開後のファイルサイズがほぼ同じ
(約3,039,374バイト vs 約3,040,074バイト、差はわずか700バイト)。
これはTesseractの構造上の既知の制約で、**縦書き専用に文字認識精度を
高く再学習したネットワークが別途存在するわけではなく**、実体としては
横書きとほぼ同じLSTM認識ネットワークに、縦書きレイアウト解析のための
設定差分が乗っているだけ、という可能性が高い(未確認の推測ではなく
ファイルサイズから読み取れる事実。Tesseractのモデル内部構造まで
逆コンパイルして確認したわけではない点は留保する)。**つまり
「縦書き用モデルへの切り替え」自体は正しく機能しているが、それだけで
横書きと同等の文字認識精度が保証されるわけではない**、という前提を
はっきりさせておく。

### 3. 文字の誤認識 と 列の読み順/ルビ/見出しの混入 の切り分け

**未実施。実機で撮影された実際の本のページの画像が無いと、この切り分けは
推測に頼らざるを得ない。** 推測で「おそらくこちらが原因」と決め打ちする
ことは、指示書の「文脈から文章を補って正しく読めたことにしない」という
要求に反すると判断し、今回は行っていない。

ただし、切り分けに使える技術的な足場は用意できる状態にあることを確認
した。`worker.recognize()`は既定で`data.text`(結合済みの全文)だけで
なく`data.blocks`(段落・行・単語ごとのバウンディングボックス・信頼度
つきの階層構造)も返している。現在の実装(`ocr.ts`)は`data.text`のみを
候補として使っており、見出し・ページ番号・ルビ等が別ブロックとして
検出されていても区別せず結合されている可能性がある。**次に実際の写真で
問題が再現した際、`data.blocks`を見れば「1つの塊の中で文字が化けている
(認識誤り)」のか「複数の塊が読み順どおりでなく混ざっている(レイアウト
解析の問題)」のかを区別できる。** 今回はこの分析基盤の存在を確認した
だけで、UIやロジックの変更は行っていない(根拠なく先回りして実装しない、
という基本方針どおり)。

### 4. 原本からOCR用画像を作る際の縮小

**問題を発見し、修正した。** `src/lib/fieldnote/camera.ts`の
`MAX_CAPTURE_DIMENSION`(撮影画像の長辺の上限)が**1600px**に設定
されており、この値は保存用画像とOCR用画像の両方(同じBlobを共用して
いる)に適用されていた。iPhoneのカメラは通常この値よりはるかに高い
解像度で撮影できるため、1600pxへの縮小は、密な縦書き(1ページに
数十列を収める本が多い)の各文字が占める画素数を大きく減らし、複雑な
字画を持つ漢字の認識を妨げていた可能性が高い、と判断した。

**1600 → 2600に引き上げた**(`getUserMedia`の`width`/`height`の
`ideal`制約も同じ定数を参照しているため連動して変更される)。数値を
無制限に上げなかったのは、IndexedDBの保存容量とOCRの所要時間への
影響を考慮したため(トレードオフの詳細は「将来の変更可能性」参照)。

## 検証・未検証事項

**検証済み:**
- 上記1・2は実際にPlaywright(Chromium)で動作確認した(向きの保持、
  実際のネットワークリクエストでの縦書き学習データの使用)。
- `npx tsc --noEmit` / `npm run build`: エラーなし。
- 既存のFieldnote回帰(23項目)、連続撮影・再開・候補確認の自動テスト
  (14項目)、いずれも今回の変更後も全件PASS。

**未検証(このセッションでは確認できない):**
- **解像度引き上げが実機での縦書き精度を実際に改善するかどうか。**
  このサンドボックスにはiPhone実機も、実際に紙の本を撮影した写真も
  無いため、確認できない。
- **解像度引き上げによる実機でのOCR所要時間・IndexedDB消費量への
  影響。** 画素数が約2.64倍(2600²/1600²)になるため、OCR所要時間が
  増える可能性がある。速度は「十分」との報告だったため一定の余地は
  あると見ているが、実測が必要。
- **文字の誤認識とレイアウト解析(読み順・ルビ・見出し)の切り分け。**
  上記3のとおり、実際の写真が無いと診断できない。

**プロジェクトオーナーに実物の写真の提供を依頼する。** 前回iPhoneで
テストした際と同じ写真(複数ページ分あれば尚良い)をこの会話で共有して
いただければ、その画像データをそのままChromium上のテストハーネスに
注入し(カメラを介さず、実際に撮影されたバイト列をIndexedDBのcapture
レコードへ直接書き込む)、修正前(1600px相当に縮小し直したもの)と
修正後(2600pxのまま)の両方でOCRを実行し、認識結果全文と所要時間を
実測値としてそのまま報告する。**Chromiumで実行するため、実機Safariでの
所要時間そのものとは異なりうるが、画素データ自体は同一であるため、
文字認識精度の比較としては有効な代理検証になる**(速度の絶対値では
なく、修正前後の相対的な変化を見る用途と位置づける)。

## 採用理由 (Rationale)

- 「実機修正済み」と決め打ちせず、確認できたこと・できなかったことを
  明確に分けて記録するのは、このセッション全体(Decision Log 0192)の
  方針と一貫している。
- 解像度の引き上げは、実測なしでも「密な縦書き文字の画素数不足」という
  技術的に説明のつく具体的な原因に対する直接的な対策であり、実装上の
  リスクも低い(既存のアーキテクチャ・UIを変更しない、単一の定数変更)
  ため、実物写真の到着を待たずに先行して適用した。
- ルビ・見出し混入の切り分けや、そのための表示・ロジック変更は、
  実際の失敗パターンを見ないまま実装すると、存在しない問題への対策
  (無駄な複雑化)か、見当違いの対策になるリスクが高いため、証拠が
  揃うまで実装しないことにした。

## 他の案 (Alternatives)

- 画像の解像度を上げず、代わりにOCR前に画像を拡大(アップスケール)
  してからTesseractに渡す案も検討したが、既に失われた画素情報を
  補間で作り出すだけであり、実際に高い解像度で撮影することに比べて
  効果が薄いと判断し、まず撮影解像度自体を上げる方を優先した。
- `data.blocks`を使った見出し・ルビ除去ロジックを先に実装する案も
  検討したが、上記のとおり実写真での検証が先だと判断し見送った。

## 将来の変更可能性 (Future changes)

- 提供される実物写真での検証結果次第で、`MAX_CAPTURE_DIMENSION`を
  さらに調整する(足りなければ上げる、所要時間が実機で許容できない
  水準まで悪化すれば下げる、あるいは保存用とOCR用で別々の解像度を
  持たせる設計に変更する)可能性がある。
- 実写真で「複数ブロックの混在」が実際に問題だと判明した場合、
  `data.blocks`を使って本文らしき最大のブロックを優先する、といった
  具体的なロジックを新しいDecision Logエントリとして追加する。

## Research Context

「まだ直っていないかもしれない」ことを技術的な根拠とともに正直に書き
続けることは、このスタジオの「未完成をそれらしく見せない」姿勢の実践
そのものである。特に今回は、実写真が無いという制約の中で「確認できた
こと」と「推測に頼らざるを得ないこと」を混同しないよう、意識して分けて
記録した。
