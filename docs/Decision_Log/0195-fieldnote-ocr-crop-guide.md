# 0195 — OCR用の固定ガイド枠による切り出しを追加

## Decision

Decision Log 0193で実写真によるOCR精度調査を行った結果、**撮影フレーム
全体(背景の書類・物まで)をそのままOCRに渡していたことが、精度低下の
主因の一つ**と判明した(実写真での比較結果は下記「実測結果」を参照。
写真本文・認識結果の実際の文字列はここには含めない)。これを受け、
プロジェクトオーナーの指示に基づき、撮影画面に本のページを置くための
固定ガイド枠を表示し、その枠の範囲だけをOCRに渡す仕組みを実装した。

自動的なページ境界検出・台形補正は、この基本動作(固定枠での切り出し)
が実写真で効果を確認できてから次の段階で検討する(指示書どおり、今回は
実装しない)。

## 実装したこと

1. **カメラ画面に固定ガイド枠を表示**(`src/pages/fieldnote/index.astro`
   の`#ocr-guide-frame`、`app.ts`の`GUIDE_FRAME_RECT`)。画面(実際には
   `<video>`の表示領域)に対する割合で定義した、静かな見た目の矩形
   (白い枠線のみ、操作を要求しない)。
2. **原本Blobは一切変更せず、撮影時に範囲だけを記録する**。
   `camera.ts`に`mapScreenRectToCaptureRect()`を追加した。`<video>`は
   `object-fit: cover`で表示しているため、画面に見えているガイド枠の
   位置と、実際に撮影される映像全体は一致しない(はみ出た部分が
   中央から均等に切り取られて表示されている)。この変換を行わずに
   画面上の割合をそのまま適用すると、ガイド枠に合わせて撮ったつもりの
   範囲と実際に切り出される範囲がずれるため、この変換を正しく行う
   ことを実測で確認した(下記「検証」参照)。結果は`ocrCropRect`
   (`FieldnoteCapture`の新フィールド、原本の幅・高さに対する割合+
   回転角度)として、撮影の瞬間に記録に書き込む。
3. **OCR実行時に、その範囲だけを切り出してから認識する**
   (`src/lib/fieldnote/ocr.ts`の`cropForOcr()`)。回転が指定されて
   いる場合は、切り出す前に原本画像自体を中心周りに回転させる(台形
   補正ではない、単純な平面内回転のみ)。切り出し後の画像を、既存の
   `resizeForOcr()`(Decision Log 0194、OCR専用の縮小)にそのまま渡す。
   原本のBlob・IndexedDB上の記録は一切書き換えない。
4. **撮影後、範囲を小さくプレビュー表示。通常は調整不要**。各記録の
   OCRブロックに「読み取り範囲を確認・調整」という折りたたみ式の
   小さなプレビュー(原本の縮小画像+切り出し範囲の枠)を追加した。
   既定では閉じており、そのまま「読み取る」を進められる
   (Decision Log 0192の「画面を簡潔にする」方針を維持)。
5. **ページがずれたときだけ調整できる**。上記のプレビューを開くと、
   範囲の位置・大きさ・回転を5つのスライダーで調整できる。「この範囲で
   読み取り直す」を押すと、その記録の`ocrCropRect`を更新し、既存の
   再試行と同じ経路(`ocrQueue`)でOCRを再実行する。
6. **向き・回転・範囲は、撮影・再試行・再訪後の処理のいずれでも同じ
   フィールド(`ocrCropRect`/`ocrOrientation`)を読み書きする一本の
   経路**(Decision Log 0192で確立した`ocrOrientation`の扱いと同じ
   パターン)。既存レコード(この機能より前に撮影された記録、または
   何らかの理由で範囲が記録されなかった記録)は`ocrCropRect`が
   未設定のままとなり、その場合は原本全体を使う(下位互換)。

## 検証結果

**検証済み(Playwright、Chromiumの自動テストによる):**
- ガイド枠の画面上の位置(割合)から、実際の映像解像度・表示領域の
  大きさをもとに独立して計算した「期待される切り出し範囲」と、
  実際に記録へ保存された`ocrCropRect`が一致すること(`object-fit:
  cover`によるはみ出しクロップを含めて正しく変換されていること)を、
  幾何計算を伴うテストで確認した。
- 範囲調整UI(5つのスライダー)で値を変更すると、プレビューの枠が
  即座に反映され、「この範囲で読み取り直す」を押すとその値どおりに
  `ocrCropRect`が更新され、再度OCRが実行されること。
- 調整後の範囲・向きが、履歴から記録を開き直した後も保持されている
  こと(調整パネルを開いたときのスライダーの初期値も、直前に調整した
  値から始まること)。
- 撮影中断(`pending`のまま閉じた記録)からの再開処理でも、向き・
  回転を含む範囲がそのまま維持されて処理されること。
- 既存のFieldnote機能回帰(23項目)、連続撮影・再開・候補確認の自動
  テスト(14項目)、サイト全体のレスポンシブ回帰、いずれも今回の変更後
  も全件PASS。
- `npx astro check` / `npx tsc --noEmit` / `npm run build`:
  エラー・警告なし(既存の1件の無関係な警告を除く)。

**実写真での比較(プロジェクトオーナー提供の実際の書籍ページ写真、縦書き、
1枚)。写真本文・認識結果の実際の文字列は記録しない。所要時間と、
おおまかな傾向のみを記録する:**

| 条件 | 所要時間 |
|---|---|
| フレーム全体(背景含む)をOCRに渡す | 約9.4秒 |
| ガイド枠相当の範囲(ページ部分のみ)に切り出してOCRに渡す | 約3.9秒 |

切り出しありの方が、処理時間が短く(画素数が減るため)、認識結果に
背景の物体・他の書類由来と見られる無関係な断片が混入する度合いが
体感的に少なかった。**ただし、切り出しても文字の誤認識自体は残って
おり、縦書きOCRが横書きと同等の精度に達しているとは言えない**
(Decision Log 0188・0193の結論から変わらず)。

**未検証:**
- 固定ガイド枠の大きさ・位置(`GUIDE_FRAME_RECT`)が、実際の様々な
  本のサイズ・実機での構え方に対して適切かどうかは、実機での複数回の
  試用でしか判断できない。
- 回転調整の実際の使い勝手(実機でページの傾きをどの程度正確に
  補正できるか)は未検証。
- 実機(iPhone)のカメラが実際に提供する映像解像度・アスペクト比は
  機種依存であり、このサンドボックスのfakeカメラ(検証時は3840×2160
  を提供)とは異なりうる。`mapScreenRectToCaptureRect()`の変換式
  自体はアスペクト比に依存しない一般的な計算だが、実機での見た目の
  確認はできていない。

## 採用理由 (Rationale)

- 実写真での比較により、切り出しの有無が既存の解像度調整
  (Decision Log 0193)よりも実際の精度・速度に与える影響が大きいと
  判断できたため、優先して対応した。
- 「固定ガイド枠+都度調整可能」という設計は、指示書の「まずは固定
  ガイド枠による切り出しで十分」という要求どおりであり、自動ページ
  境界検出のような複雑な画像処理を今の時点で実装しない、という
  CLAUDE.mdの「使う予定が確認できていないものを先に作らない」方針
  にも沿っている。
- 原本と切り出し画像を分離する設計(Decision Log 0194で確立した
  「原本を上書きしない」原則の延長)により、後から範囲を調整して
  読み取り直せる(原本さえ残っていれば、何度でもやり直せる)。

## 他の案 (Alternatives)

- ガイド枠をユーザーがドラッグで動かせるようにする(撮影前に位置を
  調整する)案も検討したが、「静かなガイド枠」「連続撮影の操作感を
  保つ」という要求と、実装の複雑さ(タッチ操作・端末間の差異への
  対応)を踏まえ、今回は固定位置+撮影後の調整のみとした。
- 範囲調整UIを、ドラッグ&リサイズ可能な矩形編集(いわゆる画像
  トリミングツール)にする案も検討したが、タッチジェスチャの実装・
  検証の複雑さに対して、スライダーでも同じ結果(位置・大きさ・回転の
  指定)が得られるため、まずはスライダーで実装した。

## 将来の変更可能性 (Future changes)

- 実機での試用結果次第で、`GUIDE_FRAME_RECT`の値、範囲調整UIの
  操作方法(スライダー→ドラッグ操作等)を見直す可能性がある。
- 「まずは固定ガイド枠による切り出しで十分」という前提が実機検証で
  裏付けられた場合、次の段階として自動ページ境界検出・台形補正を
  別のDecision Logエントリで検討する。

## Research Context

実写真での検証結果を「実装前の推測」ではなく「実際に測った事実」として
記録しつつ、写真本文や認識結果の具体的な文字列はDecision Logやコミット
に含めない、という今回の記録の仕方は、個人の読書記録という性質上、
検証の透明性と本人のプライバシーの両立を図ったものである。
