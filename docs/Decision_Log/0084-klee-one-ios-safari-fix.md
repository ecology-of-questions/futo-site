# 0084. Klee OneがiOS Safariで表示されない不具合を修正する

- 日付: 2026-09-04
- 状態: 採用中(0082を一部上書き)

## Decision

プロジェクトオーナーから「スマホ版が全てのページにおいてあらゆる更新が
されていない」という報告を受け調査した。実機のスクリーンショットから、
Hero見出し「気づいたら、そこに問いがある」がKlee One(手書き調
フォント、Decision Log 0082)ではなく、フォールバックのYu Mincho等で
表示されていることが判明した。プライベートブラウジングでも同じ結果
だったためブラウザキャッシュの問題ではなく、また、この不具合より後の
コミット(FormspreeのForm ID修正、Decision Log 0076)は実機で正常に
動作確認できていたため、デプロイ全体が古いわけでもないと判断できた。
PCブラウザでは正しく表示されるとの確認も得たため、iOS Safari固有の
問題に絞り込んだ。

原因は、Klee Oneの自己ホストを「文字種ごとに`unicode-range`を分けた
2つの`@font-face`(同一`font-family`・同一`font-weight`)」として
実装していたこと(Decision Log 0082)だった。同一family/weightに対して
unicode-rangeだけで住み分けた複数の`@font-face`は、一部のWebKit系
ブラウザ(iOS Safariを含む)で、片方のファイルしか読み込まれない・
どちらのファイルが選択されるか不安定になることがある既知の癖がある。

対応として、`fontTools`(Pythonライブラリ)を使い、2つのwoff2
(漢字チャンク・かな/記号チャンク)を1つのwoff2に統合し、
unicode-rangeを使わない単一の`@font-face`に変更した。文字集合
(「気づいたら、そこに問いがある」に含まれる文字のみ)は変更していない。

- `public/fonts/klee-one/klee-one-600-kanji.woff2` +
  `klee-one-600-kana.woff2` → `klee-one-600.woff2`(1ファイルに統合)
- `src/styles/global.css`の`@font-face`を2つから1つに統合

## 採用理由

- unicode-range分割そのものをやめて単一ファイルにする方法は、
  ブラウザの実装差異に依存する挙動を根本的に排除できる。今回の
  文字集合はもともと1つの短い見出し文字列(13文字)専用の小さな
  サブセットのため、統合しても合計ファイルサイズはほぼ変わらない
  (分割時41KB→統合後40KB)。unicode-rangeによる「必要な文字だけ
  読み込む」という最適化のメリットは、この規模ではほぼ意味がなく、
  安定性を優先する方が合理的だった。
- `fontTools`によるマージは、Google Fonts配布ファイルの改変(文字の
  デザイン変更等)を一切伴わない、単純なグリフ集合の結合であるため、
  フォント自体の見た目・ライセンス上の性質は変えていない。

## 他の案

- unicode-rangeの記法を見直す(範囲の重複除去等)案も検討したが、
  そもそも「同一family/weightに対する複数@font-face」という構成
  自体が一部ブラウザで不安定になりうるため、構成そのものを単一化
  する方が確実だった。
- Google Fonts CDNを直接`<link>`で読み込む案(自己ホストをやめる)も
  検討したが、Decision Log 0082で自己ホストを選んだ理由(この開発
  環境からのCDN到達性、必要な文字だけに絞った軽量な配信)は今回も
  変わらないため見送った。

## 将来の変更可能性

- このセッションの環境にはWebKit(Safari相当)のブラウザエンジンが
  なく、実際のiOS Safariでの動作確認はプロジェクトオーナーの実機に
  委ねている。マージ後、改めてiPhone等での表示確認をお願いしたい。
- 将来Klee Oneを他の見出しにも展開する場合、文字集合を追加するには
  `fontTools`で新しい文字を含む形に再度マージし直す必要がある
  (tokens.cssの`--font-hero-heading`コメントに手順の前提を明記済み)。

## Research Context

デザイン上の意図(見出しに「ふと」の手触りを宿らせる)が、実装の
細部(unicode-rangeの分割方法)によって一部の閲覧環境だけで実現され
ない、という状態は、この研究室が大切にしている「観察」の姿勢を
そのまま実装作業にも要求する出来事だった。プロジェクトオーナーからの
「更新されていない」という一見漠然とした報告から、実機のスクリーン
ショット・PCとの比較・タイミングの整合性を1つずつ確かめて原因を
絞り込んだ過程は、Decision Logが「なぜ」を積み重ねる記録であることの
実践例でもある。
