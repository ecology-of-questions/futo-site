# 0039. 研究断面詳細ページの表をセクション右下に回り込み配置し、図版・表の回り込みを「グループ」として独立させる

- 日付: 2026-08-16
- 状態: 上書き済み(→ 0040)。表の回り込み配置(float: "right")自体を
  撤回し、表は全幅表示に戻した。`groupBlocks()`/`.floatGroup`の
  仕組み自体は削除し、図版の回り込みは元の`clear: both`方式に
  戻している。詳細はDecision Log 0040を参照。

## Decision

`TableBlock`型(`src/types/researchReview.ts`)にも`ImageBlock`と同様の
`float?: "right"`を追加し、研究断面01のセクション3の表に指定した。
プロジェクトオーナーの「表の右下に配列して、左下には文章」という
依頼への対応。

実装にあたり、単純に表へ`float: right`を付けるだけでは意図通りに
ならないことが分かった。セクション3の図1(Decision Log 0038)が
既に右上でfloatしており、表の直後に続く5つの段落は、そのDOM上の
位置(前の段落からの通常フローの続き)だけで見ると、図1の回り込み
範囲を消費し終えた時点で既に表の開始位置に到達してしまい、表の
回り込み範囲には一切かからない、という結果になった(floatは通常
フローの高さに寄与しないため、後続要素の縦位置はfloatの実際の
高さを考慮しない)。

これを解決するため、`ResearchReviewArticle.astro`に`groupBlocks()`
関数を追加した。`float: "right"`を持つ図版・表と、それに直後に
連続する段落ブロックをひとつの「回り込みグループ」としてまとめ、
`.floatGroup`(`display: flow-root`)でラップして描画する。
`display: flow-root`は新しいブロック整形コンテキストを作るため、
各グループは前のグループのfloatの影響を受けず、グループ自身の
先頭からfloatと段落の回り込みが正しく計算される。

これに伴い、`.table`の`clear: both`や`.tableFloatRight`の
`clear: right`(Decision Log 0038で導入)は不要になったため削除した
(floatGroupによって回り込みが自己完結するため)。

## 採用理由

- floatによる回り込みは、同じブロック整形コンテキスト内での
  「そこまでの通常フローの蓄積高さ」に強く依存する、content-length
  に対して壊れやすい仕組みである。今回のように図版と表という
  2つの回り込み要素が同じセクション内に存在する場合、意図した
  「相手」ではなく前の要素の回り込みに文章を消費されてしまう
  問題が起きた。
- `display: flow-root`による回り込みグループの分離は、標準的な
  CSSの機能(新しいBFCは既存のfloatをまたがない)を使った解決策で、
  JavaScriptでの高さ計算やmagic numberのマージン調整を必要と
  しない。
- `groupBlocks()`はfloatを持つブロックと後続の段落を自動的に
  検出してグループ化する汎用的なロジックにしたため、02以降の
  Reviewページで図版・表を回り込み配置する際も、コンテンツ側は
  `float: "right"`を指定するだけでよく、特別な入れ子構造を
  authoring側で意識する必要がない(Decision Log 0030以来の
  「元原稿の構造をそのまま表示する」というフラットなブロック配列
  モデルを維持できた)。

## 他の案

- 図版・表と段落の入れ子構造を`ContentBlock`型自体に持たせる案
  (例: `MediaRowBlock { media, text }`)も検討したが、既存の
  フラットな配列モデルからの乖離が大きく、コンテンツ記述側の
  負担も増えるため見送った。`groupBlocks()`による自動グループ化の
  方が、既存のデータモデルを壊さずに済む。
- 表の回り込み開始位置を、`margin-top`の固定値で図版の高さぶん
  ずらす案も検討したが、図版の高さやテキスト量が変わるたびに
  値を再調整する必要があり、壊れやすいため採用しなかった。

## 将来の変更可能性

- 02以降のReviewページで図版・表を複数回り込み配置する場合も、
  `groupBlocks()`が自動的にグループ化する。ただし、回り込みグループの
  直後に別の回り込みグループが来る場合(段落を挟まない場合)の
  挙動は今回のケースでは検証していないため、実際にそのようなコンテンツが
  出てきた際に確認が必要。

## Research Context

図版・表それぞれが「自分の直後の文章とだけ関係を持つ」独立した
かたまりとして振る舞うようにしたことで、原稿の構造(「この図の次に
この説明がある」「この表の次にこの考察がある」)が、レイアウト上も
そのまま対応関係として保たれるようになった。技術的な回避策では
あるが、結果として「原稿の構造をそのまま表示する」というDecision
Log 0030以来の一貫した方針に沿う形になっている。
