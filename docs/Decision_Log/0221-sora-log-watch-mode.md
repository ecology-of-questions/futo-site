# 0221. 「みはりモード」(マイクによる自動検知)を追加する

- 日付: 2026-11-13
- 状態: 採用

## Decision

プロジェクトオーナーから、「そらのようす」の手動記録ボタンを押し忘れることがあるので、自動的に音を検知してサーバーに記録できる簡易な仕組みを作れないか、との相談を受けた。

まず、ウェブサイトからの本当の意味での「バックグラウンド録音」は技術的・プライバシー上の理由で不可能であることを説明した。ブラウザ(特にiOSのSafari/Chrome)はタブが非表示の間マイクを継続して提供しない、常時音声を取得する機能はOS側の明示的な許可・専用アプリが必要、周囲の会話など第三者の音声まで拾ってしまう懸念がある、といった理由による。プロジェクトオーナーもこれを受けて「これは何か音を採取するだけの機械を作ることになると思う」と述べ、ウェブサイトの機能としては別の設計が必要だという理解で一致した。

その後、プロジェクトオーナー自身がClaude Artifact上で「みはりモード」という名前の試作(フォアグラウンドで画面を開いている間だけ、マイクの音の大きさを端末内で数値化し、しきい値を超えて一定秒数続いたときだけ自動で1件記録する、音声そのものは録音・送信しない)を作り、「アーティファクトに、みはりモードを追加したから、HPにも反映して」との指示があった。試作のJavaScript実装を直接読み、その設計・アルゴリズムを本番の「そらのようす」に忠実に移植した。

### 実装内容

- `migrations/0005_sora_log_watch_mode.sql`: `sora_log_entries`に`source`(既定値'manual'、既存の全行は手動記録として扱う)・`duration_seconds`・`max_level_db`を追加。
- `src/components/SkyWatch.astro` + `SkyWatch.module.css`: みはりモード本体。`getUserMedia`(エコーキャンセル・ノイズ抑制・自動ゲイン調整はすべて無効化)→6段の`BiquadFilterNode`(highpass×4+lowpass×2、各Q=0.7071、試作のA特性近似をそのまま採用)→`AnalyserNode`(fftSize 2048)→125msごとに時間領域データを読み、`10*log10(meanSquare+1e-12)+94+補正値`でdB相当の数値に変換→1秒ごとにLeq(エネルギー平均)を計算→しきい値以上が続いた秒数を数え、しきい値を下回ってから2秒経過した時点で、続いた秒数が設定値以上なら1件だけサーバーに送信する、というしきい値交差の状態機械。音声データ自体を変数に保持・送信する処理は一切ない。
- `worker/index.ts`: `source`('manual'/'watch')・`durationSeconds`(0〜600)・`maxLevelDb`(0〜140)を検証して保存。手動記録とみはりモード記録で連投制限を分離した(下記参照)。
- `src/components/SkyLog.astro`: 3番目のタブ「みはりモード」として`<SkyWatch />`を追加。既存のタブ切り替えロジックは`[data-view-tab]`/`[data-view-panel]`を総称的に扱っているため無改修で3つ目に対応できた。`SkyWatch`がサーバーへの記録に成功すると`document`に`sora-log:entry-created`というカスタムイベントを発行し、`SkyLog`側がこれを購読して「記録を見る」タブの一覧・空の帯・地図にその場で反映する(2つのコンポーネントを疎結合に保つため、状態管理ライブラリは導入していない)。
- `/privacy`の10番ブロックに、みはりモードが実際に収集・送信する内容(マイクは端末内での数値化のみに使う、音声は録音・送信しない、送信するのは継続秒数と最大値のみ、画面が非表示になれば停止する)を事実のみで追記した(Decision Log 0216・0220と同じ方針)。

### 試作との違い(本番スキーマに合わせた意図的な調整)

- `loudness`は本サイトでは必須の3段階enum(`heard`/`loud`/`very-loud`)だが、試作の自動検知は数値(`lmax`)のみを保持し「きこえた」に相当する概念を持たない。しきい値を超えた時点で既に「きこえた」以上であるため、自動検知の記録では`heard`を使わず、`しきい値+15dB相当以上なら'very-loud'、それ以外は'loud'`という変換を新たに定義した。
- `kind`は自動検知では常に`'unknown'`(マイクの音量だけでは飛行機かヘリコプターか判別できない)。
- `place`は常に`'indoor'`固定(「置いて使う」想定、試作・プロジェクトオーナーの想定どおり)。都道府県・市区町村・メモはみはりモードの記録には含めない(スコープ外の単純化。必要になれば将来追加できる)。
- 連投制限: 手動記録は既存の15秒クールダウン+1日100件(`source='manual'`に絞って判定するよう変更)。みはりモードは航空機の通過が数秒〜数十秒おきに連続することがあるため、クールダウンは課さず、暴走防止のための別枠の1日200件上限(`source='watch'`に絞って判定)のみを設けた。
- キャリブレーション(試作にもあった機能): 端末のマイク・ブラウザによって数値が実際の大きさとずれるため、騒音計などの実測値に合わせて補正値を保存できるようにした。`localStorage`に保存し、サーバーには送らない(この端末・このブラウザだけのローカルな調整)。

### フォアグラウンド限定の徹底

`navigator.wakeLock`はベストエフォートの補助として使うが、それに依存せず、`visibilitychange`でタブが非表示になった時点で即座にマイクを解放し、みはりモード自体を停止する実装にした。「常時・バックグラウンドで動作する」という誤解を避けるための、意図的な設計(/privacyにも明記)。

## 採用理由

- プロジェクトオーナー自身が既に設計・試作した機能であり、再設計せずその意図(フォアグラウンド限定、音声を一切録音・送信しない、しきい値交差による自動検知)に忠実に移植することが最も妥当と判断した。
- 「公開研究室」として、記録の確からしさ(evidentiary)を保つ既存方針(時刻はサーバー側のみ、クライアントからの時刻送信・修正機能を持たない)を、自動検知の記録にもそのまま適用した。
- 手動記録とみはりモード記録の連投制限を分離したのは、試作の設計意図(連続する航空機の通過を記録できるようにする)を汲みつつ、暴走・誤作動時の無制限な記録の積み上がりを防ぐため。

## 他の案

- 「しきい値を超えた瞬間に即記録する」(継続時間を見ない)案も検討したが、試作が継続時間による判定(短い物音の誤検知を減らす)を既に導入していたため、その設計を維持した。
- `loudness`を4段階目(例: `auto-detected`)に拡張する案も検討したが、スキーマ変更の影響範囲(既存の手動記録フォーム・地図・一覧表示すべて)が大きく、15dB差という単純な変換で既存の3段階に収められたため見送った。将来、自動検知と手動記録を明確に区別する表示要件が出てきた場合は再検討する。

## 将来の変更可能性

- 現時点ではみはりモードの記録に都道府県・市区町村を付けられない。固定の場所(自宅等)に設置して使うことが多いと想定されるため、将来的に「この端末の記録には常にこの都道府県・市区町村を使う」といった設定を追加する余地がある。
- キャリブレーション値は`localStorage`のみに保存しており、端末・ブラウザを変えるとリセットされる。複数端末で同じ補正値を使いたい場合は、将来の検討課題。
- 現在は「このページを開いている間に自動記録したもの」の一覧はページ内のメモリ上にのみ保持され、リロードすると消える(サーバー側の全記録は`source: 'watch'`として永続化されているため、データ自体は失われない)。

## Research Context

「記録し忘れる」という実際の利用上の課題に対し、技術的に不可能な解(バックグラウンド録音)を安易に実装するのではなく、プロジェクトオーナー自身がその場で設計し直した、ウェブサイトとして実現可能な形(フォアグラウンド限定・導出された数値のみの送信)を正式に採用したことは、「公開研究室」が目指す、継続的な改善・共同設計のプロセスそのものを体現している。音声を一切記録・送信しないという制約を貫いたことも、「研究・報道・行政への要望・裁判などに使える公開の記録」という目的に対し、収集するデータの説明責任を保つ上で重要な設計判断である。

## 検証・未検証事項

- `npx astro check` / `npm run build`: エラーなし。
- `worker/index.ts`を独立tsconfig(`resolveJsonModule`有効)で型チェック: エラーなし。
- `wrangler dev --local`(migrations 0001〜0005適用済み)で、curlにより: 手動記録(`source`省略時'manual'扱い)が引き続き成立すること、みはりモード記録(`source: 'watch'`)が`durationSeconds`/`maxLevelDb`付きで成立し、直前の手動記録とのクールダウンの影響を受けず連続投稿できること、`source`の不正値・`maxLevelDb`の範囲外値がいずれも400エラーになることを確認した。
- Playwright(Chromium、`--use-fake-ui-for-media-stream --use-fake-device-for-media-stream`で疑似マイクを使用、390px幅)で、「みはりモード」タブへの切り替え、「開始」でのマイク使用許可・計測開始、しきい値をその場で変更してしきい値交差(開始→持続→終了)を発生させた結果、実際に`POST /api/sora-log/entries`が送信され記録が成立すること、タブを非表示にすると(`visibilitychange`)即座にみはりモードが停止しボタン表示が戻ることを確認した。コンソールエラーなし。
- `sora-log:entry-created`カスタムイベントによる「記録を見る」タブへのその場反映は、合成イベントを直接発行して検証した(一覧に自動検知の表示形式「自動検知(みはりモード)・最大XdB相当・Y秒」で正しく反映されることを確認)。
- 【未検証】このサンドボックス環境には実機のマイクが無いため、実際の環境音(本物の航空機の音等)を使った計測精度・キャリブレーションの妥当性は検証できていない。Chromiumの疑似マイクデバイスが生成する信号の正確な性質(常時無音ではない可能性がある)も未解明だが、しきい値交差の状態機械自体が正しく動作し、サーバーが受理できる範囲の値を送信することは確認できている。実環境での検証はプロジェクトオーナーに委ねる。
- Preview/Production のD1には、このコミット時点ではまだmigration 0005を適用していない(後述のとおり、プロジェクトオーナー側での実行が必要)。
