# 0187 — Fieldnote読書記録と公開本棚の統合(v3、Stage 1実装+Stage 2/3の調査・設計)

## Decision
プロジェクトオーナーから指示書「Fieldnote読書記録と公開本棚の統合 v3」を受けた。指示書自身が定めるStage 1〜3の段階分けに従い、今回のPRでは**Stage 1(個人記録の土台+3画面の整合)を実装し、Stage 2(OCR)は実際に技術調査・測定した結果を設計として記録するに留め、Stage 3(サーバー側認証付き公開API)は設計のみ記録して実装しない**。指示書自身が「設定待ちの項目を『本番で動作確認済み』とは報告しない」ことを明示的に許容しているため、この段階分けをそのまま踏襲した。

## 確認したが変更しなかった点
- **`FieldnoteMemoDemo.astro`のタブ構成の全面刷新は見送った。** 指示書の参考画像(抜粋/コメント/つながりタブのモックアップ)は「実装済み画面だと解釈しない」「寸法を固定コピーしない」という指示書自身の留保つきの構想画像であり、一方でこのデモの現行タブ構成(概要/たどる/自分のまとめ/育つ)は、Decision Log 0184でプロジェクトオーナー自身が作ったCanvasモックアップに基づく既存の情報設計判断である。どちらもモックアップ経由の構想であり、Claudeが新しい参考画像だけを根拠にどちらを優先するか(＝どういう情報を見せるデモにするか)を独断で決めるのは、CLAUDE.mdが定める「情報設計・コンテンツに関わる決定は先に確認する」領域に踏み込むと判断した。実利用に直結する個人用Fieldnote本体・公開本棚(データ・表示の正しさが実際に問われる部分)を優先し、架空データのみで完結するデモの見せ方は、指示書が明示的に要求した最小限(デモ表記の明確化・実アプリへの導線)に留めた。全面刷新が必要であれば、新しいモックアップに基づいて次回改めて実施する。

## OCR調査(Stage 2、実装せず・実測結果を記録)
指示書6節の要求どおり、「実際に動く現実的な手段」を調査し、実測せずに「一瞬で終わる」等と書かないよう、この環境で測定できる範囲で実測した。

### 調査した手段
1. **Tesseract.js(採用候補)**: WebAssembly版Tesseract OCRをブラウザのWeb Workerで動かすMITライセンスのライブラリ。画像は一切外部に送信されず、処理は端末内で完結する(「外部AIを無断で呼ばない」要件を、外部呼び出し自体が無いという形で満たせる)。
2. **Shape Detection API(`TextDetector`)**: ブラウザネイティブAPIだが、Chromium系の一部でのみ実験的に利用可能で、日本語の認識精度・対応状況が不安定なため見送った。
3. **クラウドOCR API(Google Cloud Vision等)**: 精度は高いが、画像を外部サーバーに送信する時点で指示書が要求する「無断で外部AIを呼ばない」「非公開の写真を外部に送らない」方針と衝突するため、少なくとも明示的なユーザーの同意なしには採用できない。今回は不採用。

### 実測方法と結果
このサンドボックス環境(Node.js 22、Intel Xeon 2.8GHz、4vCPU)で、`tesseract.js@5` + 日本語学習データ(`@tesseract.js-data/jpn`)を使い、以下の2条件で実測した(実機のスマートフォンでの計測ではないため、あくまで参考値として記録する)。

**条件A: 理想条件(クリーンな合成テキスト画像、傾き無し・ノイズ無し・PNG)**
- ワーカー初期化(日本語学習データの読み込み含む): 約0.8〜1.7秒(量子化モデル`best_int`で約0.8秒、非量子化`best`で約1.7秒)
- `recognize()`本体: 約0.55秒
- 文字精度: 100%(3行・約60文字の合成テキストで完全一致)

**条件B: カメラ撮影に近い条件(2.5度の傾き・軽いノイズ・JPEG圧縮を加えた同じ合成テキスト画像)**
- 処理時間はほぼ変わらず(初期化約0.8秒+認識約0.58秒)
- **文字精度は約32%まで低下し、文中に判読不能な文字化けが発生した**(例:「人間の手が」の後が「ス②ミ=こ=ぃうてかえって」のように誤認識)。

学習データのダウンロードサイズも実測した: 非量子化版(`best`)は約16MB(gzip)、量子化版(`best_int`)は約2MB(gzip)で、今回の実験では精度差は見られなかった。

### 結論・設計方針(実装は次回以降)
- 実際に撮影される本のページは、条件Bよりもさらに悪条件になりうる(ページの湾曲、遠近歪み、影、印刷書体の多様さ等)。**「写真から自動で正確に文字起こしできる」とは言えない**というのが実測に基づく結論であり、「一瞬で読み取れます」という訴求は事実に反する。
- したがって、実装する場合もOCRは**抜粋テキスト欄への下書き(プリフィル)としてのみ**扱い、常にユーザーが目視確認・修正してから保存する前提とする(現在の「抜粋は手入力」という設計を、OCR実装後も本質的には変えない)。
- 学習データの初回ダウンロード(2MB程度でも)は無断で自動実行せず、「文字を読み取る(データを約2MBダウンロードします)」のような明示的な同意付きボタン操作を起点にする。
- 撮影直後に自動実行せず、ユーザーが「読み取る」を選んだ写真のみに絞る(全キャプチャへの自動適用はモバイル回線・バッテリーへの負荷が大きい)。

## サーバー側認証付き公開API調査(Stage 3、実装せず・設計のみ)
既存の`futo-site` Cloudflare Worker(`worker/index.ts`)+D1(`futo-lab-notebooks-production`/`-preview`)は、実験室ノートの投稿API用に構築済みで、CLAUDE.mdはこのCloudflare依存を「他機能へ拡張する場合は新しいDecision Logで判断する」とスコープしている。今回は以下を設計のみ記録し、実装しない(このサンドボックスから本番Workerへ安全にデプロイ・検証できないため。指示書自身も「設定待ちの項目を動作確認済みと報告しない」ことを許容している)。

### 設計スケッチ
- **D1スキーマ**: 新規`reading_notes`テーブル(`id, book_id, author_reflection, quote, quote_location, related_records_json, published_at, updated_at`)。既存`entries`テーブルとは別テーブルにし、実験室ノートの投稿権限モデル(誰でも投稿可・レート制限のみ)と混同しない。
- **エンドポイント**: `POST /api/reading-notes`(新規作成)・`PUT /api/reading-notes/:id`(更新)・`DELETE /api/reading-notes/:id`(取り下げ)。`GET /api/reading-notes?bookId=`は認証不要(公開閲覧用)。
- **認証方式**: 訪問者向け機能ではなく運営者本人専用のため、Cloudflare Workerのsecretとして設定する管理者パスワード(例: `ADMIN_PASSWORD_HASH`、事前にハッシュ化した値のみ保存)を用いたログインエンドポイント(`POST /api/admin/login`)を新設し、成功時にHMAC署名付きセッションCookie(`HttpOnly`・`Secure`・`SameSite=Strict`)を発行する。既存の`IP_HASH_SECRET`同様、署名鍵のsecretが未設定の場合はログイン自体を500で拒否する(fail closed、弱い鍵へのフォールバックをしない)。
- **CSRF対策**: Cookieベースのセッションだけでは不十分なため、ログイン成功時に発行するCSRFトークンをレスポンスボディで返し、更新系リクエストのヘッダ(例: `X-CSRF-Token`)と照合する。
- **楽観的ロック**: `updated_at`をリクエストに含め、DB上の`updated_at`と一致しない場合は409を返す(複数タブでの同時編集による上書き事故を防ぐ)。
- **入力検証**: 既存の`handlePostEntries`と同様、文字数上限・`bookId`が`src/data/bookshelf.ts`の既存IDと一致するかのサーバー側検証を行う(クライアント側の見た目上のバリデーションだけに頼らない)。
- **XSS対策**: `authorReflection`/`quote`等はエスケープしたうえでAstro側の通常のテキスト差し込み(`{}`)で表示する(既存の`readingNoteBodyText`等と同じ、`set:html`を使わない方針を維持)。

## 採用理由 (Rationale)
- 指示書自身がStage 1/2/3を明示的に分けており、「各段階は小さいコミットに分ける」「設定待ちの項目を動作確認済みと報告しない」ことを許容しているため、この段階分けに従うのがもっとも指示に忠実。
- Stage 2/3を今回実装しなかったのは技術的困難のためではなく、(a) OCRは実測の結果、無編集での自動採用が正確性の点で正当化できないと判明したため「常に人間が確認する」設計を先に固める必要があったこと、(b) サーバー側認証はこのサンドボックスから本番Cloudflare環境へ安全にデプロイ・検証する手段が無く、CLAUDE.mdが要求する「新しいDecision Log entryでの判断」を伴う拡張だと判断したため。

## 他の案 (Alternatives)
- OCRを「撮影後に自動実行」する案も検討したが、実測の精度(条件Bで約32%)を踏まえると、確認なしの自動採用は誤情報をそのまま抜粋として残しかねず却下した。
- 公開データの反映を「Fieldnoteから直接ボタン一つで公開」にする案も検討したが、認証機構が無い現状でこれを実装すると、本来「運営者のみ」であるべき公開操作を実質誰でも実行できてしまう(指示書が明示的に禁止する「見た目だけのボタン制御」に該当する)ため、Stage 3の認証設計が固まるまでは手動コピー&ペースト運用を維持する判断をした。

## 将来の変更可能性 (Future changes)
- OCRを実装する場合は、上記「結論・設計方針」のとおり、プリフィル+手動確認必須という制約を外さないこと。
- サーバー側認証を実装する場合は、上記スケッチをベースに、実際の運用環境(Cloudflare Dashboard)で`ADMIN_PASSWORD_HASH`等のsecret設定を確認したうえで進めること。
- `FieldnoteMemoDemo.astro`のタブ構成を「抜粋/コメント/つながり」に全面刷新する場合は、プロジェクトオーナー/ChatGPTによる新しいモックアップ・情報設計の合意を先に得ること。

## Research Context
このスタジオは「公開すること」を目的化しない、という一貫した方針を持つ(CLAUDE.mdの「完成を最適化しない」)。Fieldnoteは私的な記録の道具として単体で完結し、公開はそこから本人が選んだものだけを、本人の確認を経て世に出す——という一方向の、常に人間の判断を挟む設計にした。OCRの実測結果(理想条件でも100%、現実的な条件では32%まで劣化する)は、「自動化できるように見えて実際にはできない」ことを数字で示した点で、このスタジオが繰り返し重視してきた「未完成をそれらしく見せない」という研究的誠実さの具体的な実践例になっている。
