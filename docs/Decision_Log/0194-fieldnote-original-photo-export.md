# 0194 — 撮影した元の写真を取り出せるようにする(原本とOCR入力の分離)

## Decision

「撮影した元の写真ファイルを取り出せない」という指摘を受け、写真の
保存場所・解像度を確認したうえで、以下を実装した。

## 保存場所・解像度の確認結果

- 写真はブラウザのIndexedDB(`futo-fieldnote`データベース、
  `captures`オブジェクトストア)に、各記録(capture)の`image`
  フィールドとしてJPEG形式のBlobで保存されている。外部サーバーには
  一切送信されない(この点は既存のまま変更なし)。
- 解像度は撮影時点で決まり、以後変わらない。`src/lib/fieldnote/
  camera.ts`の`MAX_CAPTURE_DIMENSION`という定数が長辺の上限を決めて
  おり、この値は**過去に複数回変更されている**(2026-09-02に導入時は
  1600px、Decision Log 0193で2600pxに変更、本エントリでさらに
  4000pxに変更・原本専用の上限として再定義)。**つまり、いつ撮影した
  写真かによって、実際に保存されている解像度が異なる。** 過去に低い
  解像度で撮影された写真の解像度は、この定数を上げても変わらない
  (Blobは撮影時点で確定しており、後から再生成する情報が無い)。
- 今回、実際の解像度をその場で確認する手段として、「元の写真を見る」
  に実際のピクセル寸法(`img.naturalWidth`/`naturalHeight`から取得、
  新しいフィールドを追加せず既存の画像から都度読み取る)を表示する
  ようにした。これにより、どの写真が低解像度(過去撮影分)で、どれが
  高解像度(本対応後の撮影分)かが、利用者からもこちらからも一目で
  分かるようにした。

## 実装したこと

1. **「元の写真を見る」は再読み込み後も開ける**(既存機能。今回の
   調査で問題が無いことを確認した。IndexedDBに保存されたBlobから
   都度Object URLを作り直しているため、リロード後も同じ写真が
   表示される)。
2. **原本に「保存/共有」ボタンを追加**
   (`src/lib/fieldnote/app.ts`の`sharePhoto()`)。Web Share API
   (`navigator.share`、ファイル共有)が使える環境ではOSの共有シート
   (「画像を保存」「AirDrop」「Filesに保存」等)を開く。使えない
   環境では`<a download>`によるダウンロードにフォールバックする。
   iPhoneのSafari(iOS 15以降)はファイル共有に対応しているため、
   これで写真をカメラロール等に取り出せるようになる見込み(実機での
   最終確認はプロジェクトオーナーに依頼、下記「未検証事項」参照)。
3. **撮影した画像(原本)とOCRに渡す画像を分離**。従来は同じBlobを
   保存にもOCRにも使い回しており、OCR用に画質を落とす=原本も画質が
   落ちる、という構造だった。
   - `src/lib/fieldnote/camera.ts`: 保存される原本の上限
     (`MAX_CAPTURE_DIMENSION`)を2600→**4000**に引き上げ、「原本用の
     上限」として役割を明確化(getUserMediaが実際に提供する解像度を
     超えて画質を作り出すことはできないため、実質的には暴走防止用の
     安全上限)。
   - `src/lib/fieldnote/ocr.ts`: 新設の`resizeForOcr()`が、原本の
     Blobを**変更せず**、OCR専用の縮小コピーを都度(呼び出しの度に)
     作ってからTesseractに渡す。このコピーはメモリ上でのみ存在し、
     保存されない。OCR用の上限(`OCR_INPUT_MAX_DIMENSION` = 2600px)
     はDecision Log 0193の実測で採用した値をそのまま踏襲した(この
     値自体の精度検証はDecision Log 0193の範囲であり、本エントリの
     変更はあくまで「保存用と分離する」ことが目的)。
4. **保存に失敗した場合は「保存しました」と表示しない。**
   `sharePhoto()`は、共有シート・ダウンロードのどちらについても、
   利用者が実際に保存を完了したかどうかをこちらから確認する手段が
   無い(OSの共有シートは「閉じた」ことは分かっても「保存を選んだ」
   かまでは分からない)。そのため、**成功を示す表示は一切出さない**
   ——実際に検出できた失敗(共有APIが例外を投げた、Blobの準備自体に
   失敗した等)のときだけエラーメッセージを表示する。利用者が共有
   シートを閉じただけ(`AbortError`)は失敗として扱わない。

## 既存データとの整合性

- 過去に保存済みの写真・抜粋・コメント等は一切変更していない
  (Blobの再生成・書き換えは行っていない)。今回の変更は今後の撮影
  にのみ影響する。
- 過去の低解像度の写真も、今回追加した「保存/共有」ボタン・解像度
  表示は同じように使える(その解像度なりの画質でしか取り出せない
  だけで、機能自体は区別しない)。

## 検証・未検証事項

**検証済み(Playwright、Chromium):**
- 「元の写真を見る」が履歴からの再読み込み後も正しい画像(実際に
  IndexedDBへパッチした高解像度の合成画像)を表示すること、実際の
  解像度(3200×4000px)がそのまま表示に反映されることを確認した。
- 「保存/共有」ボタンが存在し、クリック後に(Web Share APIが無い
  ヘッドレスChromiumのため)ダウンロードへのフォールバックが実際に
  発火すること、かつ「保存しました」という誤った成功表示が一切出て
  いないことを確認した。
- OCRを実行した後も、保存されている原本Blobのサイズ(=内容)が
  一切変化していないこと(OCR用の縮小コピーが原本を上書きしていない
  こと)を確認した。
- 既存のFieldnote回帰(23項目)、連続撮影・再開・候補確認の自動テスト
  (14項目)、サイト全体のレスポンシブ回帰、いずれも今回の変更後も
  全件PASS。
- `npx astro check` / `npx tsc --noEmit` / `npm run build`:
  エラー・警告なし(既存の1件の無関係な警告を除く)。

**未検証(このセッションでは確認できない):**
- **実機iPhoneのSafariで、Web Share APIによるファイル共有が実際に
  動作し、カメラロールやFilesアプリに保存できるか。** このサンドボックス
  にはiPhone実機が無く、ヘッドレスChromiumはWeb Share APIのファイル
  共有に対応していないため、今回はダウンロードへのフォールバック経路
  しか自動テストできていない。
- **原本の解像度引き上げ(4000px上限)による、実機での撮影時のメモリ・
  IndexedDB容量への影響。** 特にiPhoneの実際のgetUserMedia映像
  ストリームがどの程度の解像度を提供するか(4000pxの上限に達するか、
  それよりずっと低い値で頭打ちになるか)は実機でしか分からない。

## 採用理由 (Rationale)

- 「原本を後から取り出せる」という要求は、そもそも撮影の目的(本の
  ページを記録として残す)に照らして本質的な機能であり、OCRの都合
  (精度と処理速度のためにどこかで画質を落とす必要がある)とは別の
  レイヤーの要求だと判断した。両者を同じBlobで済ませていたこれまでの
  設計は、単に「まだ両者の要求が衝突していなかった」だけであり、
  今回はっきり分離することにした。
- 保存/共有の成否を断定しない設計は、指示書の「保存に失敗した場合は
  『保存しました』と表示しないこと」を字義通り満たすと同時に、OS
  共有シートの結果を正確に知る手段が実際に無いという技術的な制約に
  対しても誠実な設計だと判断した。

## 他の案 (Alternatives)

- 原本をIndexedDBとは別に、File System Access API等でファイル
  システムに直接保存する案も検討したが、iOS Safariの対応状況が
  不確実であり、既存のIndexedDBベースの保存・バックアップ/エクス
  ポートの仕組み(Decision Log 0187等)と二重の永続化経路を持つ
  ことになり複雑化するため、見送った。
- OCR結果に基づいて原本を自動で「最適化(回転補正・コントラスト
  調整等)」する案も一瞬検討したが、指示書の「元画像を上書きしない
  こと」と衝突するため不採用。

## 将来の変更可能性 (Future changes)

- 実機での確認結果次第で、原本の上限(4000px)・OCR入力の上限
  (2600px)を再調整する可能性がある。
- Web Share APIが実機で期待通り動かない場合、iOS Safari向けの
  代替手段(例: 長押し保存を前提にした`<img>`表示の見直し等)を
  別のDecision Logエントリで検討する。

## Research Context

「記録として残すための原本」と「読み取りやすくするための一時的な
縮小コピー」を明確に分けるという今回の設計は、CLAUDE.mdの「container
separated from content」という基本方針を、写真という素材そのものの
扱いにまで一貫して適用した例である。
