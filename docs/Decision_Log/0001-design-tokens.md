# 0001. 色・タイポ・余白を tokens.css に一元化する

- 日付: 2026-08-04
- 状態: 採用中

## Decision

色(Paper / Ink / Accent)、タイポグラフィ、余白のスケールを
すべて `src/styles/tokens.css` の CSS Custom Properties に集約する。
コンポーネント側の CSS Modules には色や余白の値をハードコードせず、
必ず `var(--color-*)` 等のトークン経由で参照する。

## 採用理由

- 色・フォントは現時点(Hero実装時点)でまだ仮値であり、
  ChatGPT(Creative Director)側とHome全体をデザインしながら
  最終決定する予定になっている。
- 決定が後から来る前提のため、「1箇所を直せばサイト全体に反映される」
  構造にしておく必要があった。

## 他の案

- **各コンポーネントに直接値を書く案**: 実装速度は上がるが、
  色確定時に全コンポーネントを修正することになり、
  「保守性優先」の方針(キックオフ文書)に反するため見送った。
- **Tailwindのようなユーティリティクラスで管理する案**:
  そもそもTailwind不使用の方針(技術スタック合意事項)のため対象外。

## 将来の変更可能性

- 色のHEX値・フォントファミリーは、Creative Director側の最終決定を
  受けて `tokens.css` のみを更新する想定(コンポーネント側の変更は不要)。
- セクションが増えるにつれ、トークンの種類(例: セクション間の余白など)
  が増える可能性がある。その場合もこのファイルへ追記していく。

## Research Context

「ふ、と」は完成を目指すサイトではなく、研究室と一緒に育っていくことを
前提にしている(キックオフ文書「将来の前提」)。色やフォントの最終決定も、
コードが先に確定するのではなく、ChatGPTとの対話の中で少しずつ定まっていく
性質のものだと理解している。tokens.cssへの一元化は、「まだ決まっていない
ことを、決まっていないままコードに組み込む」ための構造であり、
「余白を思考時間として扱う」という思想(Design Spec 10)を、
デザインの決定プロセス自体にも適用した形と言える。
